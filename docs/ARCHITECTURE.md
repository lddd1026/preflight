# ARCHITECTURE —— 模块划分、实现方式与扩展指南

**汇报对象**：项目负责人
**汇报目的**：讲清楚这个系统是怎么搭起来的，以及**以后要加功能时该动哪一块**
**阅读前提**：不需要读代码。文中出现的都是**模块名和文件名**，不是代码。

> 如果你只想知道「现在什么状态」，看 [STATUS.md](STATUS.md)。
> 本文回答的是另一个问题：**「我想加个功能，该改哪里？」**

---

## 一、先说结论：这套东西是怎么分工的

整个系统按**职责**切成六层，一条铁律：**只能往上依赖，不能往下依赖**。

| 层 | 名字 | 一句话职责 | 认识谁 |
| --- | --- | --- | --- |
| 5 | `cli` | 命令行入口，**唯一的组装者** | 认识全部 |
| 4 | `interact` | 问人、记答案、管豁免 | 只认识 `core` |
| 3 | `understand` | 读文档、抽声明、核对证据（**会调用模型**） | `core` `detect` `runtime` |
| 2 | `detect` | 确定性检查（**绝不调用模型**） | 只认识 `core` |
| 1 | `runtime` | 模型调用 / 缓存 / 预算 / 轨迹 | 独立 |
| 1 | `core` | 数据形状、语料加载、报告、发布状态 | 独立 |
| 0 | `knowledge`（不是代码） | **全部知识**：规则、机制、不变量、档案、问题 | —— |

**这张表是实测出来的，不是设计图上抄的** —— 有一条测试用语法树读真实的
引用关系，任何"低层引用高层"的改动都会让它变红。

**为什么这条铁律重要**：它是「加东西不用改代码」能成立的前提。
如果 `detect` 能引用 `understand`，那"确定性层零 LLM"这句承诺就只能靠自觉守。

## 二、一次运行是怎么走的

以最完整的那条命令（`review`）为例，一次评审经过五个阶段：

### 阶段一：读懂这个项目有什么

- 入口是 `detect/repo.py`，它负责**把仓库读进来**：扫文件、套忽略规则、
  读文本、解析代码结构。后面所有模块都通过它拿数据，**不自己去碰磁盘**。
- 接着 `detect/probe.py` 拿这份数据去**找"会坏的东西"**：
  从依赖清单、环境模板、编排文件、代码符号、文档声明五种线索里，
  判断这个项目有没有队列、数据库、缓存、长连接、外部接口、模型调用……
- 然后是 `detect/derive.py`：拿着探测到的机制，去查
  **知识库里的矩阵**（机制 × 不变量），推导出"这个项目该查哪些东西"，
  并为每一条生成**推理链**（因为看到了什么，所以要求查什么）。

这一阶段的产出：**一份"该查什么"的清单，每条都带理由和文件位置。**

### 阶段二：确定性检查

- `detect/engine.py` 是调度器：拿到一组规则，逐条跑在仓库上，收成一份评审结果。
- 每条规则交给 `detect/registry.py` 找到对应的**检查器**。
  检查器分四类实现：
  - `detect/generic.py` —— 通用型，**靠参数就能表达一类规则**（比如"某文件必须存在"）
  - `detect/ast_checks.py` —— 需要看代码结构的
  - `detect/cross_checks.py` —— 需要把多个文件放在一起比的
  - `detect/agent_checks.py` + `detect/agent_analysis.py` —— agent 专项那 14 条，
    其中分析内核负责回答"循环在哪、模型调用在哪、工具分发在哪"
- 有三条规则不自己实现，而是**编排现成的专业工具**（密钥扫描、依赖漏洞、静态缺陷），
  实现放在 `detect/adapters/`。**没装那些工具时，规则明确报"跳过"，不假装通过。**

这一阶段的产出：**一份确定性的问题清单。零模型调用、零联网、完全可复现。**

### 阶段三：文档层（会花钱，可选）

- `understand/discover.py` 先**找出项目里有哪些文档、各自是什么角色**（纯确定性）。
- `understand/claims.py` 让模型把文档里的**可验证声明**抽出来，
  并**立刻用代码核对每一句引用是不是原文**（模型改写或编造的直接丢掉）。
- `understand/mapping.py` 决定每条声明**该怎么验**：能用确定性规则的先用规则，
  模型只做兜底。
- `understand/verify.py` 真的去验，算出**文档兑现率**。
- `understand/guard.py` 是最后一道关：**结论的每一个字段都由代码独立复核**
  （路径存在吗、行号在范围内吗、片段对得上吗、符号在语法树里找得到吗），
  任何一项对不上就降级。

这一阶段的产出：**哪些文档说法和代码不一致。**

### 阶段四：问人

- `interact/questions.py` 算出**还剩哪些必答问题**。它只问三类问题：
  代码回答不了的、会改变结论的、文档里还没说的。
- 答案存在 `interact/store.py` 管的目录里 —— **跟着仓库走版本控制**，
  因为那是项目的决定，团队要共享、CI 要看见。

### 阶段五：出报告 + 定生死

- `interact/waiver.py` 把豁免应用上去：谁批准的、什么时候批的、为什么、什么时候到期。
  **过期的豁免自动失效**，问题原样报回来。
- `core/release.py` 装配出最终那份 `RELEASE_REVIEW.md`：
  结论 → 自动检查 → 文档兑现率 → 待人工签核 → 豁免记录。
- 退出码由 `cli.py` 根据**没被豁免的**问题算出来。

## 三、逐模块说明

### 3.1 `core/` —— 地基（8 个文件）

这一层**不认识任何业务逻辑**，只有数据形状和读写。

| 文件 | 干什么 | 怎么实现的 |
| --- | --- | --- |
| `models.py` | 全项目的数据形状：规则、机制、不变量、档案、发现、评审结果 | 用数据校验库定义，格式错了在加载期就报 |
| `registry.py` | **把磁盘上的知识变成可用的对象** | 扫描知识目录、逐文件校验、再做交叉引用检查（规则指向的机制/不变量必须存在） |
| `specs.py` | **检测能力的声明表**：有哪几种查法、各自要什么参数 | 纯声明，和实现分开；写规则时用错参数会在这里被挡住 |
| `claims.py` | 文档层的数据形状：文档、声明、证据、结论 | 同上 |
| `interact.py` | 人工层的数据形状：问题、答案、豁免 | 同上 |
| `report.py` | 终端和 Markdown 两套渲染 | 所有来自项目的文本都做转义，防止格式串被当成标记 |
| `release.py` | 最终评审报告的装配与渲染 | **纯函数** —— 同一份状态渲染两次必须字节相同，日期存在状态里而不是渲染时取 |
| `__init__.py` | 包版本号 | —— |

**什么时候要动它**：只有**新增一种数据结构**时才动。
普通加规则、加机制**不需要碰这一层**。

### 3.2 `runtime/` —— 运行期基础设施（6 个文件）

| 文件 | 干什么 | 怎么实现的 |
| --- | --- | --- |
| `llm.py` | 模型调用 | 零依赖的兼容客户端打底（覆盖主流云服务和本地部署），可选的第三方库作为增强 |
| `budget.py` | 预算闸门 | 调用前后各记一次账，超了直接停 |
| `cache.py` | 响应缓存 | 键 = 文档指纹 + 提示词版本，所以同样的输入第二次不花钱 |
| `trace.py` | 轨迹落盘 | 每一步的输入输出都写下来，事后能复盘 |
| `paths.py` | **运行期状态放哪里** | **绝不放在被检查的仓库里** —— 这是硬约束，检查工具不许改变被检查的东西 |
| `__init__.py` | 导出 | —— |

**什么时候要动它**：**换模型供应商**只动 `llm.py`；调整预算/缓存策略动对应文件。
这一层和业务完全解耦。

### 3.3 `detect/` —— 确定性检查（18 个文件，最大的一层）

这一层的红线是**绝不允许调用模型**，有一条测试直接扫源码守着。

| 文件 | 干什么 | 怎么实现的 |
| --- | --- | --- |
| `repo.py` | 被检查的仓库 | 文件扫描 + 忽略规则 + 读文本 + 解析代码结构，**结果带缓存**（每个文件最多读一次） |
| `base.py` | 检查器接口 | 所有检查实现共用的一套约定 |
| `registry.py` | 检查器实现表 | 名字到代码的映射；**声明了没实现、实现了没声明都会报错** |
| `engine.py` | 调度 | 逐条跑规则、收集发现、记录跳过的规则 |
| `generic.py` | 通用检查器 | 靠参数表达一类规则，**不需要为每条规则写代码** |
| `ast_checks.py` | 结构类检查 | 解析代码语法树 |
| `cross_checks.py` | 跨文件检查 | 把多个文件放在一起比 |
| `agent_analysis.py` | **agent 代码分析内核** | 找出"循环在哪、模型调用在哪、工具分发在哪"，供上面那些检查器调用 |
| `agent_checks.py` | agent 专项 14 条 | 调用上面的内核 |
| `probe.py` | **机制探测** | 五类线索（依赖/环境模板/编排文件/代码符号/文档声明），每条命中都带位置 |
| `derive.py` | **矩阵推导** | 机制 × 不变量 → 检查项，每条生成四环推理链 |
| `ignore.py` | 忽略机制 | 让用户能说"这一条我知道，别报"；**被吃掉的条数会计数，不静默丢弃** |
| `adapters/` | 外部工具编排 | 只做编排和结果归一化，**一行规则都不自己实现** |

**什么时候要动它**：

- 加一条**普通规则** → **不用动这一层**，只写知识文件
- 加一条**需要新查法**的规则 → 动 `core/specs.py`（声明）+ 这一层（实现）+ `registry.py`（注册）
- 加一种**新的外部工具** → 只在 `adapters/` 加一个文件

### 3.4 `understand/` —— 文档理解（6 个文件）

| 文件 | 干什么 | 怎么实现的 |
| --- | --- | --- |
| `discover.py` | 文档发现与分类 | **纯确定性** —— 按文件名规则和内容特征判断角色，不花钱 |
| `claims.py` | 声明抽取 | 分块 + 提示词 + 结构化输出 + **三道代码核对**（引用得是原文、得是承诺而不是计划、结构上得说得通） |
| `mapping.py` | 声明 → 验证策略 | **确定性优先**：能对到已有规则的先用规则，模型只兜底；对不上的诚实说"查不了" |
| `verify.py` | 四类验证器 + 兑现率 | 存在性/数量/约束/行为；**口径不精确时不判漂移** |
| `guard.py` | **防幻觉核对器** | 结论的每个字段由代码独立复核，对不上就降级 |
| `__init__.py` | 导出 | —— |

**什么时候要动它**：改提示词或抽取规则动 `claims.py`；
改"哪些声明怎么验"主要动**知识文件**，必要时动 `mapping.py`。

### 3.5 `interact/` —— 人工层（4 个文件）

| 文件 | 干什么 | 怎么实现的 |
| --- | --- | --- |
| `questions.py` | 问卷引擎 | 三个来源决定一条问题不用问：已答过、文档里说了、条件不满足 |
| `store.py` | 落盘 | 放在被检查仓库的记录目录里；**只有显式命令才写**，检查命令一律只读 |
| `waiver.py` | 豁免 | 规则 + 可选文件范围；**只看未过期的**；被吃掉的逐条记录 |
| `__init__.py` | 导出 | —— |

**什么时候要动它**：加/改必答问题主要动**知识文件**（但有 ≤5 的硬约束，
有一条测试实测着）；动豁免的匹配规则才动 `waiver.py`。

### 3.6 `cli.py` —— 命令行（1 个文件，1300+ 行）

15 个命令，分三组：

| 组 | 命令 | 作用 |
| --- | --- | --- |
| 入门 | `version` `demo` | 看版本；**离线演示，不配密钥不联网** |
| 确定性 | `run` `list-rules` `explain` `knowledge-check` `mechanisms` | 跑评审、看规则、看机制推导 |
| 完整 | `review` `docs` `claims` `verify` `ask` `answer` `waive` `waivers` | 端到端评审、文档层、人工层 |

**什么时候要动它**：**加一个面向用户的命令**。

## 四、⭐ 扩展指南 —— 加功能的对照表

**这是本文最该被用起来的一节。**

### 4.1 常见需求 → 动哪里

| 我想…… | 改哪些文件 | 要写代码吗 | 要加测试吗 |
| --- | --- | --- | --- |
| **加一条检查规则** | 知识目录的规则文件 + 正反例夹具 + [RULES.md](RULES.md) | ❌ **不用** | ✅ 正例 + 反例**都要** |
| **加一个机制**（新的"会坏的东西"） | 知识目录的机制文件（探测线索 + 矩阵格子） | ❌ **不用** | ✅ 三份不同技术栈的夹具 |
| **加一条不变量** | 知识目录的不变量文件 + 相关机制的格子 | ❌ **不用** | ✅ 矩阵格子数会跟着变 |
| **加一个场景档案** | 知识目录的档案文件（可能还要加条件问题） | ❌ **不用** | ✅ 每个档案都要能跑出报告 |
| **加一条必答问题** | 知识目录的问题文件 | ❌ **不用** | ⚠️ **必答总数有 ≤5 的硬上限**，有一条测试实测 |
| **加一种全新的检测能力** | `core/specs.py` 声明 + `detect/` 里写实现 + `detect/registry.py` 注册 | ✅ **要** | ✅ 两侧都要（声明↔实现一一对应） |
| **加一种外部工具的编排** | 只在 `detect/adapters/` 加一个文件 | ✅ 要（但隔离在一个文件里） | ✅ 用假工具做双面夹具 |
| **换模型供应商** | `runtime/llm.py` | ✅ 要（只此一处） | ✅ 用一个假客户端 |
| **改文档分类规则** | 知识目录的文档角色表 | ❌ **不用** | ✅ 每个角色一份应有/不应有 |
| **改"哪些声明能验"** | 知识目录的验证映射表；必要时 `understand/mapping.py` | 多数时候不用 | ✅ 正反例 |
| **改报告格式** | 终端格式 → `core/report.py`；评审报告 → `core/release.py` | ✅ 要 | ✅ 报告必须能从状态**逐字节重建** |
| **改退出码 / 门禁级别** | `core/models.py` 的严重度定义 + 知识目录的档案门禁 + `cli.py` 的判定 | ✅ 要 | ✅ 三条口径（无问题/有问题/已豁免） |
| **加一个命令行命令** | `cli.py` | ✅ 要 | ✅ README 必须提到每一个命令（有测试守） |
| **加一条 agent 专项检查** | 多数情况只写知识文件；要新的分析能力才动 `detect/agent_analysis.py` | 看情况 | ✅ 14 条一条都不许漏 |

**规律**：**八个需求里五个完全不用碰 Python。**
这正是「知识是数据」这条纪律想要的效果 —— 而它现在有测试守着，
不是一句口号。

### 4.2 加一条规则的具体步骤（最常做的事）

1. 在知识目录的**规则文件**里写：编号、名字、严重度、适用类型、
   一个匹配矩阵格子（机制 × 不变量）、用什么检查器查、什么参数、血案、报什么、怎么修。
2. 在**测试夹具**里给这条规则写**正例**（会触发的仓库）和**反例**（不该触发的仓库）。
   ⚠️ **两个都要** —— 只写正例的实现会在"误报"上失控，而误报比漏报更伤。
3. 跑一次完整性校验，它会告诉你漏了什么。
4. 在 [RULES.md](RULES.md) 里补一行说明。

**不需要动任何 Python。**

### 4.3 加一种新的检测能力的具体步骤

1. 在**声明表**（`core/specs.py`）里写清：叫什么名字、属于哪一类查法、要哪些参数、
   哪些是必填。
2. 在 `detect/` 里**写实现**，放到合适的那一类文件里
   （通用/结构/跨文件/agent 专项）。
3. 在**实现表**（`detect/registry.py`）里注册。
4. 两侧的测试都会红 —— 它们本来就是为了逼你两处都写。

### 4.4 **不该动的地方**

| 不要做 | 为什么 |
| --- | --- |
| 让 `core` 或 `detect` 引用更高层 | 分层一破，"零 LLM 的确定性层"就只能靠自觉守 |
| 在 `detect/` 里调用模型 | 那一层的全部价值就是**可复现、免费、可核对** |
| 把知识写进代码 | 加一条规则就得改 Python，而且改动会散落在各处 |
| 让检查命令写被检查的仓库 | 检查工具不许改变被检查的东西。只有显式命令（答题、豁免）才写 |
| 让跳过看起来像通过 | **"没查"和"查了没问题"必须是两种不同的样子** |
| 为了让它跑过而放宽判定线 | 有一条测试锁着几个关键阈值，动它会在改动里显形 |

## 五、这套结构是靠什么守住的

不是靠文档，是靠**测试**。关键的那几条：

| 守什么 | 手段 |
| --- | --- |
| 分层不被破坏 | 用语法树读真实引用关系，向上依赖直接报错 |
| 没有循环依赖 | 同上，同层之间的环也查 |
| 知识没被写进代码 | 扫源码里的字符串，出现孤立的规则/机制/不变量编号就报错 |
| 加东西真的只改数据 | **真的在临时语料里加一遍**，证明能跑起来 |
| 确定性层不碰网络和模型 | 扫源码 + 在干净解释器里看有没有被间接带进来 |
| 每条规则都有正反例 | 覆盖检查，缺一个就红 |
| 阶段测试被记录 | 计划里每个阶段在过程文档里都要有真实输出 |
| 判定线没被悄悄放宽 | 阈值绊线 |

**这一整套的来历**：四条纪律里原来有三条**没有任何东西在守**（靠人记得）。
审计之后才补上。**靠人记得的纪律，迟早会忘。**

## 六、当前的风险与缺口（需要知道的部分）
