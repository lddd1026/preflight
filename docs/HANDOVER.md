## 1. 这个项目是什么

**一个上线前的自动评审工具。** 它把「确定性检查 → 文档漂移核对 → 人工签核」收拢成一次运行，
并且记住**谁因为什么豁免了哪一条**。

一句话定位：

> CI 告诉你「测试通过了没有」。
> 它告诉你「**该做的测试有没有被做过**」。

三件事是它的立身之本：

1. **按机制 × 不变量检查，不按项目类别** —— 项目类别无穷多，
   但"会坏的东西"就十种（队列/数据库/缓存/长连接/定时任务/对象存储/外部接口/搜索索引/多区域/模型调用）
2. **agent 专项检查** —— 成本上限、上下文预算、幻觉证据核对、工具权限边界、轨迹留存，
   传统工具一个都不查
3. **防幻觉** —— 结论必须带证据，而证据的**每个字段由代码独立核对**；
   编造的会被拒（10 种编造方式全部有测试）

### 3.3 ⚠️ 环境陷阱（**这些坑都真的踩过**）

| 陷阱 | 现象 | 怎么办 |
| --- | --- | --- |
| **`setup.ps1` 默认走清华镜像** | 而当前 `.venv/pip.ini` 写的是 `pypi.org`。**重跑 setup 会把索引切回镜像** —— 那个镜像在本机**挂过**（装到一半卡死） | 要么传 `-IndexUrl https://pypi.org/simple`，要么重跑后手工改回 `.venv/pip.ini` |
| **网络很不稳** | `SSL: UNEXPECTED_EOF`、`ChunkedEncodingError`、甚至 `THESE PACKAGES DO NOT MATCH THE HASHES`（下到一半的残缺包） | 加 `--retries 20 --timeout 90`；整轮重试几次；**拉 10 次失败是常事**。装依赖失败**不等于**测试失败，别下错结论 |
| **Docker 守护进程默认没起** | `failed to connect to the docker API at npipe://...` | 先 `Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"`，等 40 秒 |
| **PowerShell 与 bash 语法不通** | `while [ $n -lt 10 ]` 在 PowerShell 里直接解析报错 | 短命令用 `pwsh`，shell 循环用 bash；**别在 `docker run ... sh -c "..."` 里塞复杂引号** —— 它要穿过三层解析，写错的脚本会"成功退出"而实际没跑 |
| **`pip install -e .` 不重新读 pyproject** | 改了 `pyproject.toml` 但本地毫无反应 | 手工重装：`pip install --no-build-isolation -e ".[dev]"` |
| **可编辑安装有残留** | 改包名之后 `import 旧名字` 仍然成功 —— 因为旧目录还在站点包里 | 卸干净再装；**验证改名成功不能只看"新名字能用"，要看"旧名字不能用了"** |

### 3.4 在 Linux 容器里验证（CI 的等价物）

```powershell
docker run --rm -v "D:\deepseekharness\preflight:/src" -v "e:\pip_cache:/pipcache" `
  -w /src -e PIP_CACHE_DIR=/pipcache python:3.11-slim sh /src/scripts/run_tests_in_container.sh
```

那个脚本带**整轮重试 10 次**（因为网络），装不上会明确报「这是网络问题，不是测试结果」。

## 5. 工作纪律（**必须守，有测试守着**）

这四条非可协商。**原来的四条里有三条靠人记得 —— 现在每一条都有东西守。**

| 纪律 | 意思 | 谁在守 |
| --- | --- | --- |
| **D1** | 阶段测试**并记录真实输出** | `tests/test_discipline.py` —— 每个阶段在过程文档里都要有真实输出块 |
| **D2** | 每条规则**同时有正例和反例**夹具 | `tests/test_rule_fixtures.py`（7 条）+ 覆盖绊线。**只写正例的实现会在误报上失控，而误报比漏报更伤** |
| **D3** | **禁止为了让测试过而放宽断言** | 一半靠阈值绊线，一半靠人。**红了先查是不是自己错了，而不是先改数字** |
| **D4** | 知识是数据，不是硬编码 | 6 条：扫源码字符串 + **行为版本**（改 YAML 就改行为） |

### 5.1 提交前必做

1. 跑 `pwsh -File scripts/check.ps1`，**全绿**才提交
2. 提交信息写清**为什么**，不只是**改了什么**
3. 一次提交一件事

### 5.2 改了东西要同步哪些文档（**有测试守着，漏了会红**）

| 改了 | 要同步 |
| --- | --- |
| 规则 | `docs/RULES.md` + 夹具 |
| 语料数量 | `README.md` 的规模数字、`docs/STATUS.md`、`docs/PROGRESS.md` |
| 计划 | `docs/PLAN.md` **和** `docs/PROGRESS.md` 两处（写清原因） |
| 任何阶段做完 | `docs/PROGRESS.md` 贴**真实输出** |
| 加了文档 | 所有文档的相对链接会进死链检查；README / STATUS 的文档地图 |

> **每加一份文档会多一条测试**（死链检查），所以测试数会 +1 —— 记得同步那几个数字。

### 5.3 几条踩出来的规矩

- **跳过 ≠ 没跑。** 「没查」和「查了没问题」必须是两种不同的样子
- **假阳性比「查不了」糟得多。** 判成漂移会让人去改一份**本来正确**的文档
- **口径不一致时不许下结论。** 「对不上」有太多无辜的解释 —— 只能说查不了
- **批量脚本要在你没预料到的形状上生效。** 出这种脚本必须**逐个文件看 diff**，不能只看「共修了 N 个文件」
- **容器是本地发现不了的问题的唯一照妖镜。** 本项目绝大多数真 bug 都是它逼出来的

## 7. 下一步能做什么（按优先级）

### 7.1 🔴 最高价值：把问卷答案真的接到严重度 / 门禁上

**为什么**：这是**唯一还没被验证的功能性缺口**。现在五条必答问题的答案
**只进报告，不改变任何结论** —— 也就是说「坏了会怎样」这个答案，
问了等于没问。

**动哪里**：

- `knowledge/questions/questions.yaml` —— 现在的 `effect:` 是**给人看的一句话**，
  要补一个**机器能读的**字段（比如"这个答案把门禁提到 X 级"）
- `core/models.py` —— 严重度需要支持"被影响面调整过"
- `cli.py` 的 `review` 命令 —— 把答案读进来、应用到判定上

**验收标准**：

- 同一个仓库，把 `blast-radius` 从「只是不好用」改到「涉及资金」，
  **退出码或严重度必须跟着变** —— 有测试证明这一点
- 报告里能区分「原始严重度」和「被影响面调整后的严重度」

**注意**：这是**行为改动**，不是加数据。按 D3，不许为了让旧测试过而放宽它们。

## 8. 最容易踩的坑（精选 6 条）

全部 18 条在 `docs/PITFALLS.md`。这 6 条是最常撞上的：

1. **本地能跑 ≠ 装得上。** wheel 曾经从第一天起就构建不出来，
   而本地一直"能跑" —— 因为开发用的是可编辑安装，**那根本不构建 wheel**。
   改动包装之后**一定要**在干净容器里装一次。
2. **"对不上"不等于"错了"。** 口径不一致（参数化让函数数≠用例数、
   目录里的辅助文件被算进工具数）会制造**假漂移** —— 那比"查不了"糟得多。
3. **同一个问题只能有一个答案。** 曾经有两个函数都在回答"路径存不存在"，
   于是结论说"找到了"、证据核对说"不存在"。**用户看到的是自相矛盾的两句话。**
4. **假失败出现两次就是真问题。** 一条会自己红的测试会训练所有人忽略红色。
   但修法是换**估计量**（三次取最快），**不是换阈值**。
5. **测试夹具不合法时，失败信息会指向被测代码。** 夹具本身要能被解析。
6. **引号穿过 shell 层级会被吃掉。** 写复杂命令就写成脚本文件，别硬塞进一层层的引号里。
