# preflight 知识本体

> **这是本项目的核心资产，比代码更重要。**
>
> 它回答一个问题：**看到这个仓库，我怎么知道该检查什么？**
>
> 上游：[OVERVIEW.md](OVERVIEW.md) ｜ 计划：[PLAN.md](PLAN.md) ｜ 规则手册：[RULES.md](RULES.md)

## 1. 为什么不做「项目类型」分类

因为项目类别是无穷的：聊天、电商、支付、IoT、游戏、编辑器、爬虫、编译器、运维平台……

如果按类型做，你要为每一种写一套检查。**而类型是举不完的。**

### 换三个能探测出来的维度

| 维度 | 问什么 | 决定 | 规模 |
| --- | --- | --- | --- |
| **不变量** | 承诺了什么「绝不允许发生」的事？ | **检查什么** | ~10 种 |
| **机制** | 用了哪些「会坏的东西」？ | **怎么检查** | ~30 种 |
| **影响面** | 坏了会怎样、涉及谁、可不可逆？ | **多严** | 3–4 维 |

**机制 × 不变量 = 可数的检查空间。**

### 一个关键验证

| 不变量 | 聊天系统里的说法 | 支付系统里的说法 |
| --- | --- | --- |
| 不能丢 | 消息不丢 | 交易记录不丢 |
| **不能重** | 消息不重复 | **不能重复扣款** |
| 不能乱序 | 会话内有序 | 流水有序 |
| 不越权 | 读不到别人的私聊 | 动不了别人的账户 |
| 不泄漏 | 内容不外泄 | 卡号不外泄 |
| 不超支 | 推送配额 | 额度限制 |

**两个看起来完全不同的行业，抽出来的是同一组不变量。** 这就是不按行业分类的理由。

## 2. 不变量清单（v1：6 个）

| ID | 不变量 | 一句话 | 违反的后果 |
| --- | --- | --- | --- |
| `no-loss` | 不能丢 | 被系统接受的数据，最终一定可达 | 用户数据丢失，不可恢复 |
| `no-duplicate` | 不能重 | 同一个操作执行多次等价于一次 | 重复扣款、重复发货 |
| `ordering` | 有序 | 定义了顺序的地方，顺序必须成立 | 逻辑错乱、状态不一致 |
| `no-unauthorized` | 不越权 | 只能碰到自己有权限的东西 | **一次越权毁掉产品信任** |
| `no-leak` | 不泄漏 | 敏感数据不出该出的边界 | 合规事故 |
| `no-overrun` | 不超支 | 成本 / 容量 / 配额有上限 | 账单爆炸、雪崩 |

> **v1 先做这 6 个。** 后续可加：`recoverable`（可恢复）、`auditable`（可审计）、
> `idempotent`（幂等，与 no-duplicate 有重叠但视角不同）、`bounded-latency`（有界延迟）。

## 3. 机制清单（v1：10 个）

| ID | 机制 | 它为什么会坏 |
| --- | --- | --- |
| `message-queue` | 消息队列 | 积压、重复投递、分区乱序、消费者崩溃 |
| `relational-db` | 关系型数据库 | 事务边界、迁移不可回滚、主从延迟 |
| `cache` | 缓存 | 击穿、穿透、**缓存键漏了租户维度 → 越权** |
| `long-connection` | 长连接 | 断线、重连风暴、状态不同步 |
| `scheduled-job` | 定时任务 | 漏跑、重复执行、执行超时 |
| `object-storage` | 对象存储 / 文件 | 上传中断、公开桶、签名 URL 过期 |
| `external-api` | 外部 API（有副作用） | 超时后不知成功与否、重复调用 |
| `search-index` | 搜索引擎 | 索引不同步、**文档级权限漏过滤 → 越权** |
| `multi-region` | 多区域 / 多副本 | 复制延迟、跨区顺序、数据驻留 |
| **`llm-call`** | **LLM 调用** | **成本不可见、上下文膨胀、幻觉、工具越权** |

> ### `llm-call` 是一个机制 —— 这一点很重要
>
> 把 LLM 调用当成一个「机制」，**agent 的全部专项检查就自动落进了同一个矩阵**，
> 不再是一个特殊分类。这是让 preflight 不做成「两个产品」的关键设计。
>
> 对照看：
>
> | 机制 | 不变量 | 检查项 |
> | --- | --- | --- |
> | 长连接 | 不能丢 | 重连补发测试 |
> | **LLM 调用** | **不能丢** | **轨迹落盘（丢了就查不出为什么错）** |
> | **LLM 调用** | **不超支** | **成本 / token 上限** |
> | **LLM 调用** | **不越权** | **工具权限边界（只读优先）** |

## 4. 矩阵：机制 × 不变量 → 检查项

**只填有意义的格子。空白表示这个组合在现实中不构成风险。**

| 机制 ↓ / 不变量 → | `no-loss` | `no-duplicate` | `ordering` | `no-unauthorized` | `no-leak` | `no-overrun` |
| --- | --- | --- | --- | --- | --- | --- |
| **`message-queue`** | 积压恢复测试<br>消费者 ack 时机<br>死信队列处理 | 消费者幂等<br>（去重键 / 唯一约束） | 分区键保证同会话有序<br>跨分区乱序断言 | — | 消息体是否含 PII | 积压告警<br>消费速率监控 |
| **`relational-db`** | 备份策略存在<br>恢复演练记录 | 唯一约束<br>幂等写入 | 事务隔离级别明确 | 行级/租户隔离<br>**ORM 查询漏 tenant_id** | 敏感字段加密<br>备份也加密 | 连接池上限 |
| **`cache`** | 缓存挂了降级行为已定义 | — | — | **缓存键含租户/用户维度** | 缓存不放敏感数据 | 缓存击穿保护 |
| **`long-connection`** | 重连补发机制 + 测试 | 客户端按消息 ID 去重 | 顺序号分配 + 测试 | 连接建立时鉴权 | — | 连接数上限<br>**重连风暴退避** |
| **`scheduled-job`** | 漏跑补偿机制 | 重复执行防护<br>（分布式锁 / 幂等） | — | — | — | 执行超时 |
| **`object-storage`** | 分片续传 | 上传去重 | — | 签名 URL 过期<br>访问控制 | **公开桶检查** | 存储配额 |
| **`external-api`** | 对账机制 | **幂等键** | — | 凭证隔离 | 传出去的数据范围 | 配额 / 限流 |
| **`search-index`** | 索引重建能力 | — | — | **文档级权限过滤** | 索引里有无敏感字段 | 索引大小 |
| **`multi-region`** | 复制延迟监控 | — | 跨区顺序定义 | 数据驻留 | 跨区传输合规 | 跨区带宽 |
| **`llm-call`** | 轨迹落盘<br>（每步 prompt / 工具 / 结果） | 重试幂等<br>（有副作用的工具） | 工具调用与结果配对 | 工具权限边界<br>高风险动作人工确认 | 密钥不进日志<br>输入不外传训练 | **成本 / token 上限<br>上下文预算<br>最大输出限制** |

**v1 实际有意义的格子约 40 个。** 这是一个人能维护的规模。

## 5. 机制怎么探测出来（不用问用户）

| 证据来源 | 能推断出 | 例子 |
| --- | --- | --- |
| **依赖清单** | 大部分机制 | `aiokafka` → 消息队列；`redis` → 缓存；`websockets` → 长连接；`asyncpg` → 数据库 |
| **代码特征（AST）** | 运行时行为 | `@scheduled` → 定时任务；WebSocket handler → 长连接；`upload` → 对象存储；`litellm` / `openai` → LLM 调用 |
| **基础设施文件** | 部署形态 | `docker-compose.yml`、k8s manifest、terraform → 副本数、多区域 |
| **配置 / 环境模板** | 外部依赖 | `.env.example` 里有 `REDIS_URL` → 缓存 |
| **文档声明** | 不变量 | README 说「离线补发」→ `no-loss`；说「多端同步」→ `ordering` + `no-loss` |
| **第三方 SDK** | 机制 + 合规 | `stripe` / `alipay` → 外部 API + PCI 类要求 |
| **数据类型** | 影响面 | 有 `id_card` / `phone` / `address` 字段 → PII |

## 6. 推理链：每个检查项都要能解释自己

**preflight 不允许输出一个没有理由的检查项。**

```
检测到：aiokafka
        来源：pyproject.toml:23
        → 机制：message-queue

检测到：README 声明「消息不丢，支持离线补发」
        来源：README.md:14
        → 不变量：no-loss

推导出：检查 mq-no-loss
        要求：存在「积压恢复」测试 + 消费者幂等测试
        结果：❌ 未通过 —— 没有找到对应的测试文件
```

**用户看到的不只是一个红叉，是「我为什么认为你需要这个检查」。**

> **一个能被反驳的工具，才是一个能被信任的工具。**

## 7. 影响面：决定「多严」，不决定「查什么」

| 维度 | 取值 | 影响 |
| --- | --- | --- |
| **涉及谁** | 内部 / 单客户 / 全体用户 / 资金 | 严重度乘数 |
| **可逆性** | 可回滚 / 不可逆 | 不可逆 → 必须人工确认 + 门禁升级 |
| **数据类型** | 公开 / 内部 / PII / 支付 / 健康 | 触发合规检查 |
| **面向** | C 端 / B 端 | B 端额外要审计、隔离、SLA、导出 |

**影响面只调整严重度与门禁，不新增"查什么"** —— 查什么永远由机制 × 不变量决定。
这条界限保证了矩阵不会被"影响面"的组合爆炸污染。

## 8. 合规：不要另起一套

合规看起来按行业分（金融/医疗/教育），最容易诱人再开一套分类。**不要。**

**把合规当成影响面的一维，靠机制探测触发：**

| 探测到什么 | 触发什么 |
| --- | --- |
| 存了身份证 / 手机号 / 地址 | 个保法 / GDPR：留存期、删除能力、加密、日志脱敏 |
| 用了支付 SDK / 有卡号字段 | PCI-DSS：不存 CVV、传输加密、密钥管理 |
| 健康数据字段 | HIPAA 类要求 |
| 面向中国大陆政企 | 等保 / 数据驻留 |

**「你存了身份证号」是可验证的事实；「你是金融行业」是猜测。** 只依据事实触发。

## 9. 探测不到时怎么办（诚实兜底）

**正确做法是承认，而不是假装没问题。**

```
⚠️ 无法判断（需要你回答）

    我在依赖里没有发现消息队列或长连接，文档里也没提到实时通信机制。
    这可能是：① 我探测得不够（请告诉我你用了什么）
             ② 项目确实没有实时需求

    请回答 3 个问题：
    1. 有没有「某个操作不能重复执行」的场景？        → no-duplicate
    2. 有没有「第三方调用后需要人工干预」的场景？    → external-api
    3. 有没有用户之间的权限边界？                    → no-unauthorized
```

**注意这三个问题是按「不变量」问的，不是按行业问的** —— 所以它们对所有项目都通用。

## 10. 维护约定

**机制、不变量、检查项都是数据文件，不是代码。**

```yaml
# mechanisms/message-queue.yaml
id: message-queue
name: 消息队列
why_it_breaks: 积压、重复投递、分区乱序、消费者崩溃
detect:
  - kind: dependency
    any_of: [aiokafka, kafka-python, confluent-kafka, amqp, pika, nats-py, pulsar-client]
  - kind: env_template
    any_of: [KAFKA_BROKERS, RABBITMQ_URL, NATS_URL]
  - kind: ast_symbol
    any_of: [Producer, Consumer, subscribe, publish]
```

**加一个新机制 = 加一个 YAML + 填矩阵里对应的格子。不需要改 Python。**

这样才能：
- 社区能贡献（贡献 YAML 比贡献代码门槛低得多）
- 公司能加内部机制
- 每一条都能被评审（「我们为什么有这条」→ 指向具体血案）
