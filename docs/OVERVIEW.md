# preflight 项目详细介绍

> 本文档回答四个问题：**要解决什么问题、为什么现有工具不够、怎么做的、边界在哪。**
>
> 上游：[README.md](../README.md) ｜ 计划：[PLAN.md](PLAN.md) ｜ 知识内核：[KNOWLEDGE.md](KNOWLEDGE.md)

## 1. 问题

### 1.1 上线前要做的事，比工具覆盖的多得多

任何一次真正的上线评审，都包含三类动作：

| 类别 | 例子 | 现状 |
| --- | --- | --- |
| **自动检查** | 密钥、依赖漏洞、许可证、静态缺陷、覆盖 | 工具很多，但各出一份报告 |
| **存在性检查** | 回滚方案写了吗？Runbook 有吗？告警配了吗？ | 靠人记得 |
| **人工判断** | 风险等级、灰度节奏、容量评估、合规判断 | 靠会议和口头确认 |

**结果是：没人能回答「这次上线到底能不能上、谁批的、带着哪些问题上的」。**

### 1.2 而这个要求对 agent 更严重

agent 系统上线前要额外检查：成本上限、上下文预算、幻觉的依据是否可核对、工具权限边界、
轨迹留存、注入防护、模型与提示词版本固定、人工兜底路径……

**传统工具一个都不查，因为传统软件里没有这些概念。**

### 1.3 两个具体后果

**后果一：报告是散的，决定是口头的。**

你在五个工具里看到五份报告，在会议里得出一个"可以上"的结论 —— 而这个结论
和它依据的东西，没有落到任何一个文件里。

**后果二：文档和实现会悄悄分叉。**

一个真实例子（本项目作者自己的项目踩过）：

```
.env.example  第 25 行：  FIVEWHYS_MODEL=deepseek/deepseek-chat
config.py     字段名 llm_model → 环境变量 FIVEWHYS_LLM_MODEL
```

模板里的变量名代码**根本不读**。用户照着文档改模型 → 静默失效，不报错。
而所有对外展示的指标，都标着一个没生效的模型名。

**纯代码检查发现不了（代码没错），纯文档检查也发现不了（文档自洽）。
只有把两者放在一起比才能发现。**

## 2. 为什么现有工具不够

| 工具 | 它做什么 | 缺什么 |
| --- | --- | --- |
| SonarQube / Semgrep | 静态缺陷、代码质量 | 不认识 agent；不读文档；不做人工签核 |
| Snyk / pip-audit | 依赖漏洞 | 只查依赖 |
| gitleaks / trufflehog | 密钥泄漏 | 只查密钥 |
| Lighthouse / k6 | 性能 | 只测性能 |
| Langfuse / Logfire | agent 可观测 | **是运行时的观测平台，不是上线前评审** |
| OPA / policy engines | 策略门禁 | 需要你自己写全部策略 |

**它们的共同形态是「一个检查器 + 一份报告」。**

而大厂的上线评审是**一个合并的、分级的、要签字的决定**。这个形态没有开源工具在做。

> **结论：不要造一个新的 SonarQube。做那层把已有检查 + agent 新检查组装成「一次评审」的东西。**

## 3. 怎么做的

### 3.1 核心思想：不分类项目，分类「机制」和「不变量」

项目类别是无穷的。但：

| 维度 | 问什么 | 规模 | 能否探测 |
| --- | --- | --- | --- |
| **不变量** | 承诺了什么「绝不允许发生」的事？ | ~10 种 | 从不变量清单 + 文档声明 |
| **机制** | 用了哪些"会坏的东西"？ | ~30 种 | 依赖清单 / AST / 配置 / 文档 |
| **影响面** | 坏了会怎样、涉及谁、可不可逆？ | 3–4 维 | 从数据类型/合规字段探测 |

**机制 × 不变量 = 可数的检查空间。**

例：不是「这是聊天项目」，而是

```
探测到：aiokafka（消息队列）、redis（缓存）、websockets（长连接）
文档声明：「消息不丢」「多端同步」
影响面：处理用户私密内容（PII）

推导出：消息队列 × 不能丢 → 必须有积压恢复测试
        长连接   × 不能丢 → 必须有重连补发测试
        文档声明「多端同步」→ 必须有对应 E2E 用例（去哪找？测试文件里找）
        PII 影响面 → 越权用例必须存在 + 日志不能打消息内容
```

**整个过程没有出现「聊天项目」。** 换一个技术栈，同一个框架自动给出不同的一组检查。

### 3.2 三层覆盖

| 层 | 规模 | 来源 | 状态 |
| --- | --- | --- | --- |
| **通用层** | ~25 条 | 内置（密钥、依赖、异常、回滚、Runbook…） | 穷举完了 |
| **机制层** | ~40 格 | 机制 × 不变量矩阵，由探测推导 | 穷举完了（v1 先做 10×6） |
| **声明层** | 不定 | **项目自己的文档** | **不需要穷举 —— 由项目生成** |

**「类别无穷」这个担心，被第三层消化掉了。** 而第三层的实现方式就是 agent 读文档。

### 3.3 文档理解层：把「声明」和「证据」对上

这是本项目最少见的部分，也是最难的部分。

```
Step 1  发现文档     扫描并分类候选文档（README / DESIGN / RUNBOOK / .env.example / CI 配置…）
Step 2  抽取声明     抽出「可验证的断言」，带类型：
                     existence / quantity / constraint / behavior / plan
Step 3  验证（确定性优先）
                     凡能用文件存在性 / grep / AST / 跑命令验证的，绝不交给 LLM
Step 4  报告不一致    ✅ 声明确认 ｜ ❌ 声明未兑现 ｜ ⚠️ 无法验证
```

**产出最有价值的东西：文档兑现率。**

```
文档兑现率  87%  (33/38 条声明)
  ❌ 5 条未兑现
  ⚠️ 4 条无法验证
```

### 3.4 防幻觉：agent 提出，代码复核

LLM 读文档做检查，最大的风险是它编造「我在第 42 行找到了」。

| 威胁 | 对策 |
| --- | --- |
| 编造文件路径 | 声称的路径必须真实存在 |
| 编造行号 | 行必须存在，且**原文片段要能匹配** |
| 编造符号 | 声称的函数/类名必须在 AST 里找得到 |
| 「我觉得应该没有」 | 无证据只允许报 ⚠️，不许下结论 |

**原则：agent 提出假设，代码复核证据。**

### 3.5 三种检查的顺序

```
① 确定性（免费、可靠） → ② 文档理解（花钱，只处理语义判断） → ③ 人工（只问剩下的）
```

**顺序是产品设计。** 反过来的话问卷会变成 60 条，没人填。

### 3.6 每次运行都输出「我的推理链」

```
检测到：aiokafka                  ← pyproject.toml:23
        README 声明「消息不丢」    ← README.md:14
推导出：检查 mq-no-loss
   → 未通过：没有找到积压恢复测试
```

**用户看到的不只是一个红叉，是「我为什么认为你需要这个检查」。**
一个能被反驳的工具，才是一个能被信任的工具。

## 4. 边界（明确不做什么）

| 不做 | 为什么 |
| --- | --- |
| 自己实现传统安全检查（漏洞/许可证/静态缺陷） | 打不过积累了十年的工具 → **只做编排** |
| 运行时观测 / APM | 那是 Langfuse / Logfire 的领域。preflight 是**上线前**，不是运行时 |
| 替代 CI | CI 说「测试通过了没」，preflight 说「该做的测试有没有被做过」 |
| 猜行业（"你是金融行业"） | 猜测不可靠。**探测到「存了身份证号」才是事实** |
| 保证「上线不出事」 | 它不保证任何事。它只保证**检查该做的被做过、决定有记录** |

## 5. 与五问法的关系

本项目的技术内核（证据核对、轨迹、成本闸门、固定模型 + 缓存 + 评测）与作者另一个项目
**fivewhys**（agent 驱动的根因分析）共用同一套方法：

| | fivewhys | preflight |
| --- | --- | --- |
| 不问 | 「这是什么故障？」 | 「这是什么项目？」 |
| 而是问 | 「证据支持哪个假设？」 | 「探测到的特征需要什么检查？」 |
| 输出 | 根因 + 依据 | 检查项 + 依据 |
| 必须能核对 | 依据来自真实工具调用 | 检查项来自真实文件 / 依赖 / 文档行 |

**不是两个项目，是同一套方法解两个问题。**
