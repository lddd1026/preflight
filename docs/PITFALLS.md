> 或者一条此后一直绿着的测试。

## 一、最容易骗过自己的那一类：**只在"装完之后"出现的问题**

这三个是本项目最值钱的发现，因为它们**在本地永远看不见**。

### 1. wheel 从第一天起就构建不出来

```python
# pyproject.toml
[tool.hatch.build.targets.wheel]
packages = ["src/preflight"]                    # 这已经把 knowledge/ 打进去了

[tool.hatch.build.targets.wheel.force-include]
"src/preflight/knowledge" = "preflight/knowledge"   # 又打一遍 → 重复路径
```

```
ValueError: A second file is being added to the wheel archive
at the same path: `preflight/knowledge/claims/verification.yaml`
```

**拖了八个阶段才发现。** 因为开发全程用 `pip install -e .` ——
**可编辑安装根本不构建 wheel。**

> **"本地能跑"和"装得上"是两件事。**
> 而后者只有真去构建一次才知道。

**修完之后加的守卫**：一条**真的执行 `pip wheel` 并检查内容**的测试。
任何"读一遍 pyproject 配置看看对不对"的替代方案都发现不了那个 `ValueError`。

### 2. 把字节码当文本读

```python
# 看起来毫无问题
for path in sorted(root.rglob("*")):
    if path.is_file():
        path.read_text(encoding="utf-8")
```

装完之后崩：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xf3 in position 0
```

pip 装包时会**字节码编译**，于是 `demo/__pycache__/*.pyc` 也在那个目录里。

**为什么本地不崩**：本地那个 `__pycache__` 是我**跑过一次之后**才生成的 ——
"本地能跑"纯属时间巧合。

**守卫**：一个单元测试测 `_is_source_file()`。
为什么不像第 1 条那样测整体？因为"今天 wheel 里没有 `__pycache__`"是一个**事实**，
而"读到字节码要跳过"是这条代码的**性质** —— 性质不会因为构建配置改了而失效。

### 3. 渲染层把长路径折成两行

Linux 的 80 列终端里，rich 把一个长路径软换行成 `.../a-r` + `ule.yaml`。

后果不只是测试红：**用户复制那个路径会拿到垃圾。**

**为什么 Windows 上绿了八个阶段**：那几个终端恰好更宽。

**守卫**：一条把终端宽度**固定成 40 列**的测试。
一个"只在特定终端宽度下出现"的 bug，不固定宽度的测试就是碰运气。

## 二、判断分寸类：**"对不上"不等于"错了"**

这一类坑不会让程序崩，只会让它**说得不对** —— 而"说得不对"更伤，
因为用户会照着它去改一份本来没问题的东西。

### 4. 口径不一致时，"对不上"有太多无辜的解释

文档说「**5 个工具**」，我数出 7 个 `.py` 文件 —— 因为目录里还有
`__init__.py` 和 `_render.py`。

文档说「**19 个测试**」，我数出 17 个函数 —— 因为**参数化会把一个函数变成好几个用例**。

> **判成漂移会让人去改一份本来正确的文档，而那比"查不了"糟得多。**

**修法**：给计数目标加一个 `exact: bool`（**数据**）。
不精确时只报「查不了」，并说清为什么。

### 5. 符号缺失是弱证据，路径缺失是强证据

「OpenAI 兼容端点」里的 `OpenAI`、「LLM 调用」里的 `LLM` —— 都被当成了符号名，
然后当然找不到，于是一批**正确**的声明被判成漂移。

而路径是精确的：`scripts/setup.ps1` 要么在要么不在。

**修法**：只有**路径**缺失才判漂移；符号缺失只能说"我认不出这个词"。

**代价是故意接受的**：`ToolRegistry` 这种纯驼峰认不出来了 ——
认不出来只是少一条证据，认错会让正确的声明变成假漂移。

### 6. 同一个问题**两个答案**

结论用的 `exists_in_repo`（会试包根目录、按文件名全仓库找）和证据核对用的
`_check_path`（只看仓库根）**不是同一个函数**。

于是同一条声明里：结论说"路径找到了"，紧接着证据核对说"路径不存在"，
最后被降级成"查不了"。**用户看到的是自相矛盾的两句话。**

**修法**：`_check_path` 直接调 `exists_in_repo`。
修完"证据没通过核对"从 5 条降到 **0**。

> **同一个问题只能有一个答案。** 两个函数回答同一个问题，就一定会有一天对不上。

## 三、API 细节类：**标准库里那些"看起来对"的写法**

### 7. `lstrip("./")` 剥的不是前缀，是字符集

```python
".venv/pip.ini".lstrip("./")   # → 'venv/pip.ini'   ← 开头的点被吃掉了
```

`lstrip` 的参数是**字符集合**，不是前缀。于是 `.venv/pip.ini` 变成 `venv/pip.ini`，
一条**正确**的证据被判成"路径不存在"。

**修法**：只剥字面量的 `"./"`：

```python
if cleaned.startswith("./"):
    cleaned = cleaned[2:]
```

### 8. YAML 里以 `*` 开头的值会被当成别名引用

```yaml
why: **没演练过的备份等于没有备份**   # ← 语法错误：*是别名引用
```

**这个坑我踩了三次。** 而多行值更麻烦：加了引号之后，原来的"折叠标量"就不再合法，
续行会被当成新的标量。

**教训**：同一个坑踩到第三次，就该把它变成一条检查。
（目前还没有 YAML 值的 lint —— 记在遗留问题里。）

### 9. AST 子串匹配会撞出一堆无关的东西

`Base` 命中了 `BaseModel`、`Database`、`base_url` ——
于是一个**没有数据库的项目**被"探测"出了关系数据库机制。

**修法**：精确匹配。`want in name.casefold()` → `name.casefold() == want`。

### 10. 工具把自己讲机制的文档当成了"本项目用了它"的证据

preflight 的 `docs/KNOWLEDGE.md` 里有一张讲机制的表格，里面写着「多区域」——
于是它探测出**「preflight 有多区域机制」**。

**这一类误报最致命**：用户会觉得"这个工具在瞎报"，然后**不会再跑第二次**。

**修法**：**只有弱线索不算探测到**。要算探测到，至少得有一条
依赖 / 配置层面的线索。弱线索单独报出来，连同理由 ——
用户扫一眼就知道"哦，它只是看到我文档里提了一句"。

## 四、测试自己也会骗人

### 11. 测试夹具本身不是合法 Python

`test_guard.py` 的夹具内容是 `line one` / `line two` —— 那是**语法错误**
（两个标识符挨在一起），于是 `Repo.parse` 返回 `None`，符号核对**整条失效**。

> **测试夹具不合法时，失败信息会指向被测代码，而真正的问题在夹具里。**

### 12. 夹具"看着干净"，其实不干净

我临时拼了一个 `{"app.py": "x = 1"}` 当干净仓库 —— 它**没有 `.gitignore`**，
于是 `general/env-not-ignored` 报了一个 blocker。

**修法**：用仓库里那套**真正评审过**的夹具（有一条验收测试保证它零发现）。

### 13. 测试假设"只有一个 blocker"

豁免测试写的是"豁免一条之后就不该再拦"，而夹具里有**两个** blocker。
豁免一个，另一个照样在 —— **代码是对的，测试是错的。**

**修法**：断言改成"**那一条**没了"，并补一条"只豁免一个，另一个该继续拦" ——
后者比原来那条更有价值：它守住"豁免不能变成一豁免全放行"。

### 14. 我的检测器把代码当成了散文

文档一致性测试里的 markdown 链接正则，把

```python
tools[call.name](**call.args)
```

这行 **Python** 当成了链接指向 `**call.args` ——
于是两份**本来正确**的文档被判"有死链"。

> **改检测器，不是改文档。** 文档没问题，是检测器把代码当成了散文。

## 五、一行批量脚本能造成的破坏

### 15. 一个"看起来只改一种东西"的脚本，改到了另一份数据文件

我给机制 YAML 写了个"给以 `*` 开头的值加引号"的脚本。它**把 glob 模式也当成了一类**：

```yaml
- "**/SECURITY*"   →   '"**/SECURITY*      ← 前面的引号被粘上去了
```

于是 **S4 的文档分类规则全坏掉，6 个测试红了**。
而那一轮我本来根本没打算动那个文件。

> **这类脚本的产出必须逐个文件看 diff**，不能只看"共修了 N 个文件"。
> 我当时的输出就是一行 `共 8 个文件` —— 而那 8 个里有一个不该被碰。

## 六、产品设计上的三条分寸

### 16. 死数据比没有更糟

我给两个 SaaS 档案写的 `include`，全都是**本来就会被选中**的规则 ——
它们读起来像"这个档案有额外要求"，实际什么都没做。

**而那会让人以为门禁比实际更严。**

**修法**：改成真的跨 `applies_to` 边界，并加一条测试
`test_no_profile_has_a_noop_include`。

### 17. 空格子是最有价值的信息

矩阵里某个「机制 × 不变量」没有规则覆盖 → 那是一个**没人管的风险区**。

把它**显式报出来**，比"我们查了 29 条规则"有用得多：
前者是风险，后者只是工作量。

### 18. 没有到期日的豁免，是一个口头决定

豁免必须有四样：**谁 / 何时 / 为什么 / 到期**。

少了最后一样，它会一直生效到某天有人想起来为止 ——
而那时已经没人记得为什么。

**到期自动失效**是这个机制里唯一真正的约束：
不需要任何人记得去删它。

## 附：这一路最省时间的三个习惯

1. **在真实项目上跑，而不是在夹具上跑。**
   S3 的 67 个假阳性、S5 的 9 个缺陷、S8 的 3 个装包问题 ——
   **一个都不是夹具发现的。**

2. **报告要连着分母读。**
   "文档兑现率 95%" 听起来很好 —— 而它的分母只有 43/204。
   把 161 条"查不了"算进分母是 20%，算进分子是 95% —— **两个都是假的。**

3. **先跑，再想为什么。**
   这个项目里最难修的 bug，没有一个是我"看出来"的。
