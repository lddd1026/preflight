## 0. 四条执行纪律

这四条是为了防止「做完了但站不住」。**每一条都可以被客观检查。**

| # | 纪律 | 反例（禁止） |
| --- | --- | --- |
| **D1** | **每个阶段结束必须跑阶段测试，并记录结果** | 「功能写完了，测试后面补」 |
| **D2** | **每条规则必须同时有「正例」和「反例」fixture** | 只测「能报出来」，不测「干净代码不误报」 |
| **D3** | **禁止为了通过测试而放宽断言** | 断言太严 → 改成 `assert x is not None` |
| **D4** | **知识（规则/机制/不变量/检查项）必须是数据文件，不是硬编码** | 加一条规则要改 Python 代码 |

> **D2 是最容易被偷偷违反的一条。** 一个只会报警的 linter 和一个只会沉默的 linter 一样没用。
> 每条规则的验收是**同时**通过：脏 fixture 报出来、干净 fixture 不报。

## 1. 模块划分

```
preflight/
├── src/preflight/
│   ├── knowledge/      ← 知识本体（数据，不是代码）
│   │   ├── invariants/     不变量定义
│   │   ├── mechanisms/     机制定义 + 探测方式
│   │   ├── rules/          规则（通用 + agent 专项 + 矩阵规则）
│   │   └── profiles/       场景档案（跑哪些规则、门禁多严）
│   │
│   │   ⚠️ 原计划里还有一层 checks/（机制 × 不变量推导出的检查项）。
│   │     实现 S0 时发现它和 rules/ 是同一个概念 —— 都是"一条检测 + 一个触发
│   │     条件"，区别只在触发条件是"总是"还是"探测到某机制"。已合并成一种 Rule，
│   │     用 matrix 字段表达所属格子。矩阵因此变成**视图**而不是第二份数据源。
│   │     详见 [PROGRESS.md](PROGRESS.md) 的设计决策记录 #1。
│   │
│   ├── core/           ← 引擎（把知识跑起来）
│   │   ├── models.py       Finding / Claim / Rule / Mechanism / Review / Waiver
│   │   ├── registry.py     加载 + schema 校验 + profile 过滤 + 矩阵视图
│   │   ├── engine.py       三阶段调度：确定性 → 文档 → 人工
│   │   └── report.py       报告渲染（终端 / Markdown）
│   │
│   ├── detect/         ← 确定性检测器（零 LLM）
│   │   ├── base.py         Detector 接口
│   │   ├── ast_det.py      Python AST：调用点 / 符号 / 关键字参数
│   │   ├── text_det.py     正则 / 字符串集合比对
│   │   ├── exists_det.py   文件 / 目录 / 配置项存在性
│   │   └── adapters/       外部工具编排（pip-audit / gitleaks / ruff）
│   │
│   ├── understand/     ← 文档理解层（LLM）
│   │   ├── discover.py     文档发现与分类
│   │   ├── claims.py       声明抽取（prompt + schema）
│   │   ├── mapping.py      声明 → 验证策略（确定性优先）
│   │   ├── verify.py       证据核对
│   │   └── guard.py        防幻觉：路径/行号/片段真实性校验
│   │
│   ├── interact/       ← 人工清单与签核
│   │   ├── questions.py    问卷引擎（最小必答 + profile 展开）
│   │   └── waiver.py       豁免（谁 / 何时 / 为什么 / 到期）
│   │
│   ├── runtime/        ← 基础设施
│   │   ├── llm.py          模型调用（复用 fivewhys 的设计）
│   │   ├── cache.py        响应缓存（文档指纹 + 模型版本）
│   │   ├── budget.py       token / 成本闸门
│   │   └── trace.py        轨迹落盘
│   │
│   └── cli.py          ← 命令行
│
├── tests/
│   ├── fixtures/           正例 / 反例仓库
│   └── ...
└── docs/               ← 本文档体系
```

### 模块依赖方向（单向，不允许反向依赖）

```
knowledge  ← 所有人都读它，它不依赖任何人
   ↑
  core  →  detect / understand / interact
   ↑
  cli
runtime 被 core / understand 使用
```

### 各模块职责与验收

| 模块 | 职责 | 验收标准 |
| --- | --- | --- |
| `knowledge` | 存所有知识：规则、机制、不变量、档案 | schema 校验通过；新增一条规则**不需要改代码** |
| `core` | 把知识跑起来：调度、汇总、报告 | 三阶段顺序可测；报告可从 Review 对象完整重建 |
| `detect` | 确定性检查，零 LLM 调用 | 每个检测器有独立单测；**全程不 import litellm** |
| `understand` | 读文档、抽声明、核证据 | 幻觉测试全绿（编造必被拒） |
| `interact` | 问卷与豁免 | 豁免有完整审计记录；问卷能跳过已答 |
| `runtime` | LLM / 缓存 / 预算 / 轨迹 | 第二次运行命中缓存；超预算会停且有说明 |
| `cli` | 入口 | 端到端可跑；退出码符合门禁约定 |

### S0 · 地基与知识格式（3 天）  ✅ 已完成

> 实际结果见 [PROGRESS.md](PROGRESS.md) 的 S0 章节。以下是当初的计划，保持原样以便对照。

**🎯 目标**：把「知识是数据」这件事立住。任何一条规则、机制、检查项都能用 YAML 描述，
加载时校验，出错时报到具体字段。

**📦 交付物**

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| PF-0 | 仓库脚手架：`pyproject.toml`、ruff / mypy / pytest、`scripts/check.ps1`、CI | `check.ps1` 全绿（哪怕只有 1 个测试） |
| PF-1 | **数据格式定义**：`Rule` / `Mechanism` / `Invariant` / `Check` / `Profile` / `Finding` / `Review` | [RULES.md](RULES.md) §1 的字段全部在 schema 里 |
| PF-2 | Schema 校验：缺字段 / 类型错 / 未知字段 → 报出**文件 + 字段路径** | 有 5 个畸形 YAML 的测试，错误信息含字段路径 |
| PF-3 | 加载器 + profile 过滤（`applies_to` / `context`） | 给定 profile 能正确过滤；有测试 |
| PF-4 | CLI 骨架：`list-rules` / `explain <rule>` | 能列出规则和它的血案描述 |
| PF-5 | 文档体系建立（本文件 + PROGRESS + RULES + KNOWLEDGE） | 五份文档交叉引用一致 |

**🧪 阶段测试**

1. `scripts/check.ps1` 全绿
2. 5 个畸形 YAML fixture → 每个都报出**指向具体字段**的错误
3. `list-rules --profile cli-oss` 与 `--profile agent-enterprise` 输出**不同**的结果集
4. **反向测试**：故意加一条 `severity: 不存在的级别` → 必须报错，不许静默通过

**✅ 退出标准**：新增一条规则只需要写一个 YAML 文件，不改任何 Python 代码。

**⚠️ 常见偷工减料**：把规则清单直接写成 Python 列表。「先能跑，回头再数据化」——
回头不会来，而且 D4 一旦破了，后面所有阶段都会跟着破。

### S1 · 确定性检测引擎（1 周）

**🎯 目标**：能对一个真实仓库跑出确定性的发现，输出可读报告。**全程零 LLM 调用。**

**📦 交付物**

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| PF-6 | `Finding` 模型 + 严重度 + 文件/行号 + 消息 + 修复建议 | 序列化往返测试 |
| PF-7 | `Detector` 接口 + 三个实现：AST / 文本 / 存在性 | 每个检测器独立单测 |
| PF-8 | 通用规则 11 条（见 [RULES.md](RULES.md) §2） | 每条一个正例 + 一个反例 fixture |
| PF-9 | 报告渲染：终端 + Markdown | 同一 Review 渲染两次结果一致 |
| PF-10 | `preflight run <path>` 端到端 | 在 fixture 仓库上跑出预期结果 |

**🧪 阶段测试**

1. **三个 fixture 仓库**：`clean/`（应零发现）、`dirty/`（应报出**每一条**通用规则）、
   `empty/`（空仓库，应优雅处理不崩）
2. 每条规则的正反例：脏 fixture 报出来、干净 fixture 不报
3. **零 LLM 断言**：`detect/` 模块下不得出现 `import litellm`（用测试断言）
4. 性能：在一个 1000 文件的仓库上 < 10 秒

**✅ 退出标准**：`clean/` 上零发现且退出码 0；`dirty/` 上退出码非 0 且报出全部 11 条。

**⚠️ 常见偷工减料**：只测「能报出来」。**必须同时测「干净的不报」**（D2）。

### S2 · 外部工具编排（4 天）

**🎯 目标**：把现成工具的输出归一化成 `Finding`。**只做编排，一行规则都不自己写。**

**📦 交付物**

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| PF-11 | `Adapter` 接口：检查工具是否存在 → 跑 → 解析 → 映射成 Finding | 有接口测试 |
| PF-12 | `pip-audit` 适配器（依赖漏洞） | 用**假工具脚本**测试解析（不依赖真实安装） |
| PF-13 | `gitleaks` 适配器（密钥） | 同上 |
| PF-14 | `ruff` 适配器（静态缺陷） | 同上 |
| PF-15 | **工具缺失时的降级**：报 ⚠️ 而不是崩，且报告里写明「未执行」 | 有测试 |

**🧪 阶段测试**

1. 三个适配器各用假工具脚本（固定输出）测解析 → 断言映射出的 Finding 字段完全正确
2. 工具不存在 → 报 ⚠️「未执行」，退出码不受影响
3. 工具输出为空 → 不报错
4. 工具返回非零退出码但输出合法 → 仍要正确解析
5. 真实工具冒烟测试（各跑一次，标记为 `slow`）

**✅ 退出标准**：三个适配器都能把真实输出转成统一 Finding；缺工具时不崩。

**⚠️ 常见偷工减料**：只测真实工具。**真实工具的输出格式会随版本变** ——
必须有假工具脚本把解析逻辑钉死，真实冒烟只是补充。

### S3 · agent 专项规则（1 周）　🏁 **v0.1 可发布**

**🎯 目标**：12 条 agent 规则全部实现，并且**在真实的 agent 项目上验证过**。

**📦 交付物**

| 编号 | 任务 | 规则 |
| --- | --- | --- |
| PF-16 | A 组：模型调用 | `no-request-timeout`、`no-output-limit`、`cost-from-price-table` |
| PF-17 | B 组：循环 | `unbounded-loop`、`tool-exception-uncaught`、`unvalidated-model-output` |
| PF-18 | C 组：上下文 | `tool-output-unbounded`、`no-context-guard`、`truncation-without-notice` |
| PF-19 | D 组：护栏与输出 | `no-budget-breaker`、`output-field-has-default`、`no-evidence-check` |
| PF-20 | **包装层识别**：配置声明 LLM 调用入口，消除包装层误报 | `--llm-entry` 配置 + 忽略机制 |
| PF-21 | 忽略机制：`# preflight: ignore <rule>` + 配置文件排除 | 有测试 |

**🧪 阶段测试（本阶段最关键）**

1. 每条规则：脏 fixture 报出来 + 干净 fixture 不报（12 × 2 = 24 个 fixture）
2. **双跑对比验证** —— 这是本阶段的核心验收：

   | 仓库 | 期望 |
   | --- | --- |
   | `fivewhys`（作者自己的项目，逐条踩过坑） | **全过**（或仅有明确的 info 级提示） |
   | `broken-agent-demo`（故意写坏的 agent） | **报出全部 12 条** |

3. **包装层误报测试**：一个把参数传在 wrapper 里的项目，配了 `--llm-entry` 后应零误报
4. 忽略机制：加了 ignore 注释后该条消失，其他条不受影响

**✅ 退出标准**：双跑对比通过。**这个对比就是 README 的第一屏。**

**⚠️ 常见偷工减料**：只在手工造的 fixture 上验证，不跑真实项目。
**真实项目才能暴露误报** —— 而 12 条规则里至少有 4 条（`no-context-guard`、
`tool-output-unbounded`、`truncation-without-notice`、`no-evidence-check`）误报风险不低。

### S4 · 文档发现 + 声明抽取（1.5 周）

**🎯 目标**：能从仓库文档里抽出**可验证的声明**，并且**准确率可度量**。

**📦 交付物**

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| PF-22 | 文档发现器：扫描 + 分类（入口/设计/需求/运维/评审/安全/约定/元数据） | 在 fivewhys 上认出全部 8 份文档 |
| PF-23 | `runtime/llm.py`：模型调用层（固定模型 + 温度 0 + 超时 + 最大输出） | 有假客户端可注入，测试不联网 |
| PF-24 | `runtime/cache.py`：文档指纹 + 模型版本 → 缓存 | 第二次运行命中率 100% |
| PF-25 | `runtime/budget.py`：单次运行 token / 成本上限 | 超限会停，且有可读说明 |
| PF-26 | **声明抽取**：prompt + 输出 schema（含 `claim_type`） | 见下方硬指标 |
| PF-27 | `runtime/trace.py`：每步落盘 | 轨迹可复盘 |

**🧪 阶段测试（本阶段有硬指标）**

1. **声明抽取准确率 ≥ 85%**：
   - 在 fivewhys 的全部文档上跑
   - 抽出 ≥ 30 条声明
   - **人工逐条核对**：是不是真声明（有没有把「动机」「背景」「未来计划」当成承诺）
   - 记录：抽对了几条、抽错了几条、漏了几条
2. `claim_type` 分类正确率：`plan`（未来计划）**不得**被当成承诺
3. 缓存：第二次运行成本 ≈ 0，且结果与第一次**完全一致**
4. 预算：故意设极低上限 → 会在中途停并说明原因
5. **离线可测**：整套测试用假 LLM 客户端跑，不联网

**✅ 退出标准**：准确率 ≥ 85%，且**漏抽率可接受**（宁可少抽，不要错抽）。

**⚠️ 常见偷工减料**：不度量准确率，看几条「差不多对」就过了。
**准确率是这个阶段的唯一交付物** —— 没有它，后面整个文档层不可信。

### S5 · 证据核对 + 防幻觉 + 报告（1.5 周）

**🎯 目标**：把声明和证据对上，并且**编造的必须被拒**。产出文档兑现率。

**📦 交付物**

| 编号 | 任务 | 验收 |
| --- | --- | --- |
| PF-28 | 声明 → 验证策略映射（**确定性优先**，LLM 只兜底） | 策略选择有测试 |
| PF-29 | 验证器：existence / quantity / constraint / behavior 四类 | 每类有测试 |
| PF-30 | **防幻觉核对器**：路径存在 / 行号有效 / 片段匹配 / 符号存在 | 见下方幻觉测试 |
| PF-31 | 漂移报告 + **文档兑现率** | 在 fivewhys 上跑出真实数字 |
| PF-32 | `constraint` 类型的诚实处理：找不到反例报 ⚠️「无法证明否定」 | 有测试 |

**🧪 阶段测试（幻觉测试是重点）**

1. **构造 10 条编造声明**，每一条都必须被拒：

   | 编造方式 | 必须的处理 |
   | --- | --- |
   | 文件路径不存在 | ❌ 拒绝，报「路径不存在」 |
   | 行号超出文件长度 | ❌ 拒绝 |
   | 行号存在但片段不匹配 | ❌ 拒绝 |
   | 符号在 AST 里找不到 | ❌ 拒绝 |
   | 只给结论不给证据 | ⚠️ 降级为无法验证，**不许报 ✅** |
   | …（共 10 种） | |

2. **人工抽查**：在 fivewhys 上跑出的结论，随机抽 10 条人工核对真伪
3. **诚实性测试**：一个声称「工具都是只读的」但无法证明否定的场景 → 必须报 ⚠️
4. 兑现率数字合理：人工估算的兑现率与工具输出差距 < 10 个百分点

**✅ 退出标准**：10/10 编造被拒；人工抽查 10 条无假阳性。

**⚠️ 常见偷工减料**：只测「能找到证据的情况」，不测「找不到 / 编造的情况」。
**防幻觉的价值全在后者。**

| PF-33 | 机制探测（依赖清单 / AST / 配置 / 文档声明） | 见下方三 fixture 测试 |

| PF-35 | **推理链输出**：每个检查项必须能说清「因为检测到什么，所以要求什么」 | 推理链含具体文件:行 |
| PF-36 | `KNOWLEDGE.md` 的 v1 矩阵（10 机制 × 6 不变量）数据化 | 与文档一致 |
| PF-37 | 探测失败时的**诚实兜底**：报「无法判断」+ 生成按不变量问的问卷 | 有测试 |

**🧪 阶段测试**

1. **三个不同技术栈的 fixture，必须推导出不同结果**：

   | fixture | 探测到 | 应推导出 |
   | --- | --- | --- |
   | `mq-service/` | 消息队列 + 数据库 | 积压恢复、消费者幂等、唯一约束 |
   | `web-api/` | 数据库 + 缓存 | 缓存越权、备份恢复、事务隔离 |
   | `batch-job/` | 定时任务 + 对象存储 | 漏跑补偿、重复执行防护、分片续传 |

2. **交叉验证**：三个 fixture 的推导结果集合**两两不相同**
3. 推理链：每一条都能追到具体文件行
4. 探测不到时：不报 ✅，而是报 ⚠️ + 问卷

**✅ 退出标准**：三份 fixture 推导正确，且推理链人类可读。

**⚠️ 常见偷工减料**：直接输出「检查项列表」不给理由。
**推理链是这个产品的核心价值** —— 用户要能判断你判断错了。

## 4. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **误报率高，用户第二次不跑了** | 致命 | D2 强制执行；S3 必须在真实项目上验证；忽略机制从 v0.1 就有 |
| **声明抽取准确率不达标** | 整个文档层不可信 | S4 设硬指标 85%；**宁可少抽不要错抽** |
| **LLM 检查成本失控** | 用户不用 | 确定性优先；缓存；单次上限；报告里公开成本 |
| **结果不可复现** | 报告不可信 | 固定模型 + 温度 0 + 文档指纹缓存（三条都进 S4 验收） |
| **知识维护爆炸（机制越加越多）** | 维护不动 | v1 只做 10 机制 × 6 不变量；知识是数据，可外部贡献 |
| **范围继续膨胀** | 永远发不出去 | v0.1 边界写死在 §3；新想法进 backlog，不进当前阶段 |
| **独立开发缺乏反馈** | 方向跑偏 | S3 的双跑验证是第一个外部检验点；之后每个版本都发 |
