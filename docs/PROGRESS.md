### 阶段测试中发现并修掉的缺陷

#### 缺陷一：表格出现零宽度列（P2，真跑一遍才发现）

`list-rules` 第一版是四列，其中「规则」和「适用」都设了 `no_wrap=True`，
两者都可能 37 字符。80 列终端下总需求超标，Rich 把**唯一可伸缩的**那列
（说明，`overflow="fold"`）压成了零宽度：

```
│ 级别 │ 规则 ││ 适用 │        ← 说明 列凭空消失
```

**单元测试全绿** —— 因为没人去看终端输出的样子。这和 fivewhys 里 FIV-12 踩的是同一个坑。

改了两版：
- 第二版让「规则」用 `ellipsis` → 零宽问题没了，但 **id 被截断成
  `message-queue/no-loss-backlog-re…`**，而 id 恰恰是你要拿去 `explain` 的东西
- 最终版**减到三列**，把规则名挪到 id 下面一行。宽度账：80 − 4 条竖线 − 6 个内边距
  = 70；级别 7 + 适用 26 之后，规则还有 37 列，正好放得下最长 id

**教训：宽度不够时该重构布局，而不是让某一列去挨饿。**
两条回归测试钉住：不许出现零宽列、id 不许被截断。

#### 缺陷二：错误信息把整份输入倒出来（P3）

pydantic 会把出错的**整个输入**塞进 `detail["input"]`。对「缺字段」这类错，
那就是整份 YAML —— 一条规则长起来能占满一屏，真正的字段路径反而被淹掉。

改成截断到 60 字符，但短值原样保留（`severity: 严重的` 就是要看到那个值）。
两条测试：长输入必须截断、短值必须原样显示。

#### 缺陷三：`explain` 把绝对路径原样铺开（P3，看输出才发现的）

```
│ 来源                                                                        │
│ D:\deepseekharness\preflight\src\preflight\knowledge\rules\no-request-timeo │
│ ut.yaml                                                                     │
```

九成是前缀，折成三行还把一个单词劈开了 —— 看起来像版面坏了。
改成能相对就相对（`src\preflight\knowledge\rules\no-request-timeout.yaml`），
不在当前目录下时才原样给（装成包时路径在 site-packages 里）。
报错信息里的文件路径也一起改了。

### 与计划的偏差

| # | 偏差 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | **`knowledge/checks/` 取消，合并进 `rules/`** | 实现时发现两者是同一个概念（一条检测 + 一个触发条件），区别只在触发条件是"总是"还是"探测到某机制" | 合并成一种 `Rule`，用 `matrix` 字段表达所属格子。矩阵变成**视图**而非第二份数据源 —— 好处是它能被推导，还能报出空格子。已同步 PLAN.md 模块树 |
| 2 | **多加了 1 条规则**（env-not-ignored，原排 S1） | 需要一条**真实**规则来证明 D4，而不是拿假数据糊弄 | 保留它。S1 的 PF-8（通用规则 11 条）因此实际只需再补 9 条 |
| 3 | **ruff 忽略 RUF001/002/003** | 中文全角标点被判成"有歧义的 Unicode"。不忽略一次报 **397 个错误**，全是标点 | 定向 ignore 并写明理由 —— 397 条噪音的结果是没人再看 ruff 输出 |
| 4 | **dev 依赖加了 types-PyYAML** | mypy 报 "Library stubs not installed for yaml" | 装存根，而不是用 ignore 压掉（压掉等于放弃类型检查） |
| 5 | **加了 `.gitattributes`** | CI 同时在 ubuntu 和 windows 上跑，换行符不一致会让任何基于文件内容的比较一边绿一边红 | `* text=auto eol=lf` |
| 6 | 阶段用时远超 3 天预估 | 单个会话内完成，但包含脚手架搭建与两次 UI 迭代 | 预估未调整 —— S1 之后再校准 |

## 设计决策记录

> 实现阶段做出的、影响后续所有阶段的决定。**每条都要写清理由。**

| # | 决策 | 理由 | 何时 |
| --- | --- | --- | --- |
| 1 | **不按项目类型分类，按「机制 × 不变量」分类** | 项目类别无穷；机制约 30 种、不变量约 10 种，可数可维护 | 计划期 |
| 2 | **传统安全检查只做编排，不自己实现** | 打不过 SonarQube / Snyk / gitleaks 十年的积累 | 计划期 |
| 3 | **`llm-call` 作为一个机制，而不是特殊分类** | agent 检查自动落进同一个矩阵，避免做成两个产品 | 计划期 |
| 4 | **三阶段顺序：确定性 → 文档 → 人工** | 反过来的话问卷会变成 60 条，没人填 | 计划期 |
| 5 | **文档理解层「确定性优先，LLM 只兜底」** | 同时降成本、降幻觉、提可信度 | 计划期 |
| 6 | **防幻觉原则：agent 提出，代码复核** | 无证据只允许报 ⚠️，不许下结论 | 计划期 |
| 7 | **规则是数据不是代码（纪律 D4）** | 否则加一条规则要改 Python，社区无法贡献 | 计划期 |
| 8 | **每条规则必须有血案字段（`incident`）** | 说不出出过什么事的，不是规则，是风格偏好 | 计划期 |
| 9 | **每个检查项必须输出推理链** | 用户要能判断你判断错了 —— 能被反驳才值得信任 | 计划期 |
| 10 | **v0.1 边界写死（S3 结束）** | 最大风险是做到第 6 周还没有能给人看的东西 | 计划期 |
| 11 | **规则只有一种，矩阵是推导出来的视图** | 两套数据源（rules/ 与 checks/）一定会分叉；一套不会。而且矩阵作为视图能报出**空格子** —— 那是没人覆盖的风险区 | **S0** |
| 12 | **`incident` 由 schema 强制非空** | 这是本项目对"什么算一条规则"的态度。只写在文档里没人遵守，写进 schema 才拦得住 | **S0** |
| 13 | **档案的 `applies_to` 不允许 `both`** | 档案必须明确站在"查软件"还是"查 agent"这一边，否则规则过滤没有基准。想通用就把规则设成 `both` | **S0** |
| 14 | **语料指纹算解析后的内容，不算文件字节** | 重命名一个文件不该让所有旧报告"过期" —— 那种信号很快没人看 | **S0** |
| 15 | **同一根目录内 id 重复 = 错误；跨根目录 = 覆盖** | 前者是静默覆盖（你改的那份可能没生效，最糟的行为）；后者是"用户自定义覆盖内置"的正常用法 | **S0** |
