## 纪律审计（D1–D4）

**这不是一个开发阶段，是一次横跨全部九阶段的复查。**
`PLAN.md` 说这四条纪律「非可协商」—— 而在这之前，其中**三条没有任何东西在守**。

| 纪律 | 之前谁守 | 现在谁守 |
| --- | --- | --- |
| **D1** 阶段测试并记录真实输出 | ❌ 靠我记得写 | ✅ `test_discipline.py`（3 条） |
| **D2** 每条规则同时有正例与反例 | ✅ `test_rule_fixtures.py`（7 条） | ✅ 加了一条覆盖绊线 |
| **D3** 禁止放宽断言 | ❌ 没人 | 🟡 **只有一半能机械化**（见下） |
| **D4** 知识是数据不是硬编码 | ❌ 没人 | ✅ `test_discipline.py`（6 条） |

**核心判断：靠人记得的纪律，迟早会忘。**

### D1：怎么机械化「记录真实输出」

「阶段测试通过」这句话**没有任何信息量** —— 它可以是猜的。
**贴一段真实输出**才让它可核对。所以判据是：

- PLAN 里的每个阶段，`PROGRESS.md` 里都要有对应小节
- 每个小节里至少有一个围栏代码块（贴了真实输出）
- 每个小节里要有「阶段测试」这一节
- 不许留「待填写」

这三条一起挡住了两种偷懒：**没做**，和**做了但没记**。

### D4：怎么机械化「知识是数据」

判据是 **`src/` 的字符串字面量里不许出现孤立的规则 / 机制 / 不变量 id**。

为什么是「孤立的字面量」这个判据：知识一旦进了代码，它的形态就是
`if rule_id == "general/hardcoded-secret"` 或者
`SEVERITIES = {"agent/no-request-timeout": "high"}` —— 两者都是一条孤立 id。

而 id 出现在**散文里**是合法甚至该鼓励的：`specs.py` 的 note 里写着
「同一个 checker 服务两条规则：`agent/no-request-timeout`……」——
**那是在解释代码，不是在把知识编进代码。**

#### 这条检查第一次跑就抓到了东西

```
runtime/cache.py:115 硬编码了 'cache'
runtime/paths.py:59  硬编码了 'cache'
```

而那里的 `'cache'` 是**操作系统的缓存目录名**，不是「缓存」这个机制 ——
两者恰好同名，因为 `cache` / `ordering` 这类**单词型 id** 就是普通英文词。

**处理方式不是放宽，是分清**：

- **规则 id**（`domain/name`）和**带连字符的机制 / 不变量 id** ——
  一律不许出现。它们不可能和英文撞车，而它们正是会被写进 `if` 的那种东西
- **单词型 id** 走一张**每条都写理由**的豁免表

而且豁免表本身有两条测试守着：
- `test_wordlike_exemptions_are_still_needed` —— **已经用不到的豁免要删掉**，
  否则下一个人会以为那里有正当理由
- `test_wordlike_exemptions_have_reasons` —— 没理由的豁免表就是「我懒得查」的名单

#### D4 还加了**行为版本**

AST 那条只说明「没有硬编码 id」，而一条把严重度写死在 checker 里的实现
也能通过它。所以另外两条真的去改数据看行为：

- 语料里写 `severity: blocker` 就报 blocker，写 `info` 就报 info
- 语料里改 `incident` 文本，读出来的规则文本跟着变

**改 YAML 就能改行为** —— 那才是「知识是数据」的实际含义。

### D3：为什么只有一半能机械化

「不许为了让测试过而放宽断言」本质上是一个**关于意图**的约束 ——
机器看不出一次修改是「修好了 bug」还是「把阈值调松了」。

能机械化的是它的**结果**：加一道**阈值绊线**。

```python
THRESHOLDS = (
    ("tests/test_acceptance_s1.py", "WALL_CLOCK_BUDGET_S = 10.0",
     "1000 个文件的扫描预算。空闲实测约 4.9 秒（约 2 倍余量）。"),
    ("scripts/check_claims_accuracy.py", "0.85",
     "声明抽取准确率门槛。PLAN 定的是 85%，实测 89.7%。"),
)
```

谁把它调松，测试就红。改表本身是可以的 —— 但那样 diff 里会明明白白写着
「我把 10.0 改成了 20.0」，而不是淹没在几百行改动里。
而且每条判定线**必须写清为什么是这个数**（有测试查）。

**真正的 D3 只能靠一条更朴素的规矩**：红了先查是不是自己错了，而不是先改数字。
而这一轮里它生效过两次：

| 现象 | 判断过程 | 结果 |
| --- | --- | --- |
| 计时测试红了 | 没动阈值，空闲重测三次：**4.79 / 4.96 / 4.89 秒**（预算 10） | 环境噪声 |
| 容器里隔离测试红了 | 源码扫描（扫 AST）两边都绿 → 我们自己的代码没问题 | **测试问错了问题** |

两次都**没有改阈值**。

### 顺带查到的一条：preflight 自己的依赖约束

D4 那一组里有一条顺手加的检查：**`pyproject.toml` 里的依赖必须写上界**。

来历有点绕 —— preflight 在 fivewhys 上**查出过一条真漂移**：
fivewhys 的 README 写着「上界 = 下一个主版本」，而它自己的 `pyproject.toml`
里有 **6 个依赖没写上界**。

**现在轮到 preflight 自己了。** 这条测试保证我们这边说的是实话。

### 阶段测试中发现并修掉的缺陷

#### 缺陷一：表格出现零宽度列（P2，真跑一遍才发现）

`list-rules` 第一版是四列，其中「规则」和「适用」都设了 `no_wrap=True`，
两者都可能 37 字符。80 列终端下总需求超标，Rich 把**唯一可伸缩的**那列
（说明，`overflow="fold"`）压成了零宽度：

```
│ 级别 │ 规则 ││ 适用 │        ← 说明 列凭空消失
```

**单元测试全绿** —— 因为没人去看终端输出的样子。这和 fivewhys 里 FIV-12 踩的是同一个坑。

改了两版：
- 第二版让「规则」用 `ellipsis` → 零宽问题没了，但 **id 被截断成
  `message-queue/no-loss-backlog-re…`**，而 id 恰恰是你要拿去 `explain` 的东西
- 最终版**减到三列**，把规则名挪到 id 下面一行。宽度账：80 − 4 条竖线 − 6 个内边距
  = 70；级别 7 + 适用 26 之后，规则还有 37 列，正好放得下最长 id

**教训：宽度不够时该重构布局，而不是让某一列去挨饿。**
两条回归测试钉住：不许出现零宽列、id 不许被截断。

#### 缺陷二：错误信息把整份输入倒出来（P3）

pydantic 会把出错的**整个输入**塞进 `detail["input"]`。对「缺字段」这类错，
那就是整份 YAML —— 一条规则长起来能占满一屏，真正的字段路径反而被淹掉。

改成截断到 60 字符，但短值原样保留（`severity: 严重的` 就是要看到那个值）。
两条测试：长输入必须截断、短值必须原样显示。

#### 缺陷三：`explain` 把绝对路径原样铺开（P3，看输出才发现的）

```
│ 来源                                                                        │
│ D:\deepseekharness\preflight\src\preflight\knowledge\rules\no-request-timeo │
│ ut.yaml                                                                     │
```

九成是前缀，折成三行还把一个单词劈开了 —— 看起来像版面坏了。
改成能相对就相对（`src\preflight\knowledge\rules\no-request-timeout.yaml`），
不在当前目录下时才原样给（装成包时路径在 site-packages 里）。
报错信息里的文件路径也一起改了。

### 阶段测试中发现并修掉的缺陷

**这一轮最有价值的部分。** 缺陷全部来自**真跑一遍**，不是来自单元测试。

#### 缺陷一：`unpinned-dependency` 在 pyproject.toml 上报出 9 条误报（P1）

逐行扫 TOML 把**键名和分类器**当成了依赖：`requires-python=`、`license=`、
`Development`、`Topic :: Software Development`…… 真正的 4 条被淹没。

同一段代码还有第二个错：`pydantic>=2.7,<3` 里 `<3` 在逗号后面，
正则按逗号截断，于是**看起来"没有上界"** —— 把写对的判成写错的。

修法：用标准库 `tomllib` 真解析（不引依赖），并且**在原文里搜回行号**
（tomllib 不给位置，但报告里没有位置就没法修）。

#### 缺陷二：`config-name-drift` 报出了文档里"举的例子"（P1）

它报了 `docs/OVERVIEW.md:42` —— 那一行是文档在**引用这个 bug 当例子**：

```
.env.example  第 25 行：  FIVEWHYS_MODEL=deepseek/deepseek-chat
```

**文档引用一个 bug 当例子，被检查工具读成了它自己犯了这个 bug。**

修法：默认 `doc_globs` 只看**配置模板**（`.env*` / `*.example` / `docker-compose*`），
不看 markdown 散文。这个取舍在风险上也对：静默失效来自**被复制走的模板**，
不来自散文。想连散文一起扫的用 `doc_globs` 显式指定。

#### 缺陷三：`exception-swallowed` 报了"有意的尽力而为跳过"（P2）

它报了 `detect/repo.py` 里的：

```python
except OSError:      # pragma: no cover —— 权限/竞态
    continue
```

那是**有意**的：一个文件 stat 不了就跳过它继续扫。确实没记日志，
但 `continue` 是控制流上的一个明确决定，作者想过这件事。

修法：只有 ``pass`` / ``...`` 算"什么都没说"，`continue` / `break` 不算。
**`pass` 的字面意思就是"这里什么都不说"** —— 这个区分比"有没有 except"准得多。

#### 缺陷四：`hardcoded-secret` 匹配到了自己文档里的占位符（P2）

它报了 `docs/RULES.md:62` —— 那行在说明这条规则的模式，里面有 `sk-...`。
而我的模式里有一条不要求长度的分支 `(?:get|getenv)\([^)]*sk-`，正好命中它。

后来发现那条分支**本来就是多余的**：正则在整行里搜，真实密钥里的
`sk-xxxx…` 已经被第一个分支匹配了。删掉它，误报消失，检测能力不变。
**linter 匹配到自己的文档，是这类工具最经典的假阳性。**

#### 缺陷五：目录形式的 glob 少写了 `/**`（P1）

`no-test-layer` 一口咬定"没有找到任何测试文件（找过：tests、test、specs）"——
而 `tests/` 明明就在那儿。

原因：`glob("tests")` 匹配的是**名叫 tests 的那个文件**，不是 tests 目录里的文件。
修法是给目录形式的模式补 `/**`。同一个错在 `no-eval-fingerprint` 上也修了。

#### 缺陷六：`--format json` 输出的是被折行的 JSON（P1）

`json.loads` 直接报 `Invalid control character`。

单元测试里 `render_json` 完全正确 —— 错的是它经过 `console.print()` 那一段路：
**rich 会按控制台宽度软折行。** 机器可读的输出不该被装饰，
改成绕过 rich 直接写 stdout。这条是 CLI 测试抓到的。

#### 缺陷七：`no-test-layer` 把 acceptance 当成了 integration（P2）

preflight 自己的 `test_acceptance_s1.py` 因为名字里有 "acceptance"
被归成集成层，于是"缺少集成测试"这条**不报了** —— 而那个文件测的是整条管线
（端到端），不是"组件之间对不对"（集成）。

**关键词太宽的后果是漏报真实缺口，比误报更糟：它让人以为覆盖到了。**
修法：把三个层次分开（integration / e2e / unit），acceptance 归 e2e。

#### 缺陷八：`ast.parse` 会"成功解析"非 Python 文件（P3）

`ast.parse("# 标题")` 返回一个合法 Module —— 因为那正好是一行 Python 注释。
一个恰好是合法 Python 的 markdown 会**静默产出一个空 AST**。

调用方都先过滤了 `.py`，所以这不是线上 bug，但它是个陷阱：
拿到"解析成功但没内容"的树比拿到 `None` 更容易写错。让 `parse` 只接受 `.py`。

### 阶段测试中发现并修掉的缺陷

#### 缺陷一：`tool_command` 是多元素命令，但适配器只取了 `[0]`（P1）

`tool_command` 可以是 `[python, myscript.py]` 或 `[docker, run, ...]`。
第一版适配器写的是 `[self._tool_command[0], ...]`，于是
`[python, script.py]` 变成 `[python, "-r", ...]` —— **脚本路径被丢掉了**，
工具跑成一个没有参数的 python 解释器。

修法：把命令前缀当参数传给 `command()`。**这个 bug 是写假工具测试时暴露的**
—— 真实工具永远发现不了它（真实场景下 `tool_command` 通常只有一个元素）。

#### 缺陷二：`Adapter` 用了 `@dataclass`，子类的 `tool` 被实例默认值覆盖（P1）

`@dataclass` 把 `tool: str = ""` 变成了字段，于是子类写 `tool = "ruff"`
只是加了个普通类属性，**实例属性 `self.tool = ""` 会遮住它**。

后果：`Review.tool_versions` 的键全变成空字符串 `{"": "0.17.0"}`。

修法：类级别配置用 `ClassVar` 显式声明，并且**不在实例上留可变状态**
（注册表里是单例，实例状态会在多次运行之间串味）。

#### 缺陷三：`pip-audit` 找不到 `.venv`（P1）

扫描器**有意忽略** `.venv` / `node_modules`，所以"仓库里有没有虚拟环境"
用文件列表判断是错的 —— 而 `pip-audit --path .venv/...` 需要看到它。

修法：新增 `Repo.path_exists()`（查真实文件系统）。
**扫描器的忽略规则管的是「我们读什么」，不管「工具能看到什么」。**

#### 缺陷四：gitleaks 的多命令形式回退从来没生效（P1）

旧版 gitleaks 遇到 `dir` 会**退出码 2 且什么都不打印**。而 `parse_json`
把"空输出"一律当成"没发现问题"（正常），于是第一次失败被读成了一次
干净的结果，回退逻辑永远走不到。

修法：空输出分两种情况 ——
**退出码 0/1 + 空输出 = 没问题；退出码 ≥2 + 空输出 + stderr = 这次参数它不认。**

#### 缺陷五：ruff 在测试文件里报 `S101`（P2）

干净仓库上一次报出 3 条 `S101：Use of assert detected`，全部来自测试文件 ——
而**测试文件里的 assert 完全正常**。

讽刺的是，这正是 `general/static-defect` 这条规则的文档里警告过的
「风格噪音淹掉真问题」，只不过这次是自己犯的。

修法：默认 `--ignore S101`。不用按路径排除的理由：ruff 的
`--per-file-ignores` 有自己的 glob 语义，写错一次就**静默失效**，
而"静默失效的排除规则"会让噪音原样回来、还让人以为已经处理了。

#### 缺陷六：`# noqa: S603` 被 ruff 自动修复删掉了（P2）

我们项目的 `select` 里**没有 S**，所以 `base.py` 里 subprocess 那行的抑制
从未被使用 → RUF100 判定"没用"→ `--fix` 把它删了。然后适配器用
`F,E9,B,S` 跑自己的代码，S603 就暴露出来了。

**教训：一个只看窄规则集的自动修复，会删掉只有宽规则集才需要的抑制。**

修法不是把抑制加回去（它还会被删），而是**让自己跑和工具要求别人跑的一样严**：
`select` 加上 `S`，并给测试目录定向豁免（假密钥、假密码、测试用的子进程）。

#### 缺陷七：preflight 用真实 ruff 在自己身上查出 2 个真问题

这是**最好的 dogfooding 结果**：`preflight-check run .` 报出

```
tests/test_adapters.py:31  F401：`CheckerSkipped` imported but unused
tests/test_report.py:52    S108：Probable insecure usage of temporary file: "/tmp/proj"
```

两条都是真的（前者是我重写一段测试时留下的死导入，后者是测试夹具里的
硬编码临时路径）。都已修掉 —— 修完之后自身评审里 ruff 那条归零。

### 阶段测试中发现并修掉的缺陷

#### 缺陷一：在真实项目上误报 **67 条**（P0）

第一次拿 `fivewhys` 跑双跑对比，14 条规则报出 **67 条**误报。
一个写得规矩、484 个测试的项目被报成这样，意味着这些规则**当时完全不可用**。

原因分五类，每一类都是"只看形状、不看语义"：

| 误报 | 条数 | 真实原因 |
| --- | --- | --- |
| `tool-output-unbounded` | 36 | 匹配了**任意** `.append()` —— 包括 `forwarded.append('--check')` 这种命令行参数列表 |
| `cost-from-price-table` | 12 | (a) `cost_per_token` 在那只是**读价格用来显示**；(b) `completion_cost` 是**兜底**，前面已经读了 provider 上报的数字 |
| `truncation-without-notice` | 8 | `_clip` 是 **CLI 表格单元格的显示助手**，不是工具输出截断 |
| `tool-exception-uncaught` | 5 | 匹配到了函数定义名 `_tool_call`（假 LLM 服务的辅助函数） |
| `model-name-scattered` | 6 | 把**文档/示例/测试**里的模型名也算成了"散落" |

逐条修法（每一条都写进了对应的规则文档）：

1. append 的接收者必须像**消息列表**（含 message / history / conversation / chat / context）
2. 价格表那条改成具名 checker：**同一个文件里有正确写法就不报**
3. 截断候选名单收窄（去掉 render / budget），**并且要求函数体里真的出现了切片**；
   另外跳过测试函数
4. 工具分发要求实参里**提到一个 name**（真正的分发一定涉及模型给的名字）
5. 模型名必须出现在**配置位置**（`model=` / `MODEL =`），并默认排除测试

**结果：67 → 0。**

#### 缺陷二：`_is_model_config_position` **匹配到空**（P0）

第一版正则用了 `\bmodel\w*\s*[:=]` —— 而 `\b` 在 `llm_model` 的**下划线后面不成立**
（`_` 是单词字符）。于是这个函数什么都没匹配到，规则退化成一条**永远不触发的空检查**。

**最可怕的地方是它看起来是通的**：fivewhys 上确实报了 0 条 ——
但那不是因为过滤对了，是因为整条规则失效了。

是 D2 的**正例测试**把它逼出来的（两个文件都把模型名写在配置位置上，却什么都没报）。

修法两处：用 `[^A-Za-z0-9]` 而不是 `\b`；允许 `model` 和 `=` 之间有**类型注解**
（`llm_model: str = "`），而且前缀是**以开引号结尾**的。
并加了一条专门的回归测试，逐一断言五种真实配置写法 + 三种不算配置的写法。

#### 缺陷三：`Field(description=…)` 被判成"有默认值"（P0）

`has_default` 里那条分支写成了 `return not value.args` —— **逻辑反了**
（空参数列表 → 返回 `True`）。

于是 `agent/output-field-has-default` 在 fivewhys 上误报：那个项目的 `Diagnosis`
**全用** `Field(description=…)`，而它的注释里甚至写着
「这些字段全部必填，一旦给了默认值就不在 JSON Schema 的 required 里」。

> **我误报了一个恰好把同一个坑写进注释的项目。**

根因不是"不够仔细"，而是**夹具只覆盖了一种写法**（反例里只写了 `Field(...)`），
所以那条分支从来没被跑到。修法：
① 正反例夹具补上三种必填写法（只有注解 / `Field(...)` / `Field(description=…)`）；
② 新增 `tests/test_field_defaults.py`，把 `has_default` 的判定表**逐行走一遍**；
③ 加一条绊线：把该函数的返回点数量钉死，改了逻辑就会红。

**这条绊线第一次响就是有效的** —— ruff 的 SIM103 让我把两条分支合并成
`return` 表达式，返回点从 8 变成 6，测试立刻红了。

#### 缺陷四：`symbol_matches` 漏掉了 `self._litellm.acompletion`（P1）

第一版只做后缀匹配（`endswith(".litellm.acompletion")`），而 fivewhys 里属性名是
`_litellm`（**下划线**，不是点），于是匹配不到。

后果很实际：缺 timeout / 缺 max_tokens 那两条规则在一个真实项目上
**完全看不到调用点**，然后安静地什么都不报 ——
而"安静地什么都不报"和"检查通过"长得一模一样。

修法：两级匹配。第二级允许符号的其余部分**作为子串**出现在前面的段里
（`_litellm` 含 `litellm`）。

#### 缺陷五：`**kwargs` 转发导致两条规则误报（P1）

真实项目里最常见的写法不是把参数写在调用点上，而是：

```python
kwargs = {"model": model, "messages": messages}
if self.timeout_s is not None:
    kwargs["timeout"] = self.timeout_s          # ← 逐键赋值
if self.max_output_tokens is not None:
    kwargs["max_tokens"] = self.max_output_tokens
await litellm.acompletion(**kwargs)             # ← 调用点上什么都没有
```

只看调用点的话，`timeout` 和 `max_tokens` **明明都设了**却会被报出来 ——
而这不是罕见写法，那是一个真实的、写得很规矩的项目。

修法：`provided_kwargs()` 会解开**同一个函数里**对该字典的赋值
（字典字面量 + 逐键赋值两种形式）。解不出来的情况（跨函数转发）仍会误报，
规则文档写明了，而且可以用 `wrapper_entry` 把注意力挪到包装层。

#### 缺陷六：preflight 用真实工具在自己身上查出的问题

- ruff 报出 `F401`（死导入）、`B007`（未用的循环变量）—— **都是真问题**
- `truncation-without-notice` 把 `render_terminal` / `render_markdown` /
  `render_json` / `_file_has_budget` 报成了截断函数 —— 而它们是**渲染器**，
  一个字符都没截。**渲染 ≠ 截断。**（见缺陷一的第 3 条）

#### 缺陷七：rich 把证据里的 `[…]` 当成标记标签吃掉了（P0）

跑完双跑对比、准备把输出贴进文档时发现：一条发现的证据本该是

```
tools[call.name](**call.args)
```

而终端上显示成

```
tools(**call.args)          ← 下标被删掉了
```

**rich 的标记语法会把任何 `[xxx]` 解释成样式标签。** 而报告是用标记语法拼的，
被检查项目的文本（证据、消息、路径、跳过原因）全是直接插进去的。

两个后果，**第一个就足够严重**：

1. **内容被悄悄改写。** 对一个评审工具来说，"证据被改写"是最不能接受的一类 bug：
   用户看不到原始内容，也就**没法核对**。而这恰恰是这个工具存在的理由。
2. **可能直接崩。** 畸形标签（`[/foo]`、`[bold`）会让 rich 抛 `MarkupError` ——
   也就是**被检查项目里的一个字符串能让报告生成失败**。

修法：所有来自被检查项目的文本一律过 `rich.markup.escape()`，
我们自己写的样式标签不转义。

**这个缺陷只在真正去看输出的时候才能发现** —— 所有测试都是绿的，
因为测试断言的是"渲染没崩"和"关键字段出现了"，而不是"内容一字不差"。
所以补了两条测试：① 方括号内容必须**原样**出现在输出里（证据/路径/血案/跳过原因）；
② 六种畸形标记不许让渲染崩。

> 留一条教训：**"渲染成功"和"渲染正确"是两件事。**
> 前者测试很容易覆盖，后者要专门盯着"内容有没有被改写"。

### ⭐ 漏抽率（召回）：退出标准的另一半

PLAN 的退出标准是「准确率 ≥ 85%，**且漏抽率可接受**」。
第一半测了，第二半一开始**没测** —— 只测精度不测召回，等于只说了故事的一半。

**度量方式**（便宜且直接）：**看那 46 条被拒的里面有多少其实是真承诺。**
拒错了就是召回损失，而且这个数字**不需要重新读一遍全部文档**。

**逐条核对结果：7 条被误杀**（约 3.4% 召回损失）。主因是「引出示例」那条过滤器：

| 被拒的引用 | 其实是不是承诺 |
| --- | --- |
| 「在 `.env` 里配好 key，跑：」 | 不是（指令）✅ 拒对了 |
| 「**它会**按需求 §6.1 的判分规则给每次诊断打分，并打印判定：」 | **是** ❌ 误杀 |
| 「触发了**会**记 `stop_reason`，并在轨迹里留一句可读的 `stop_note`：」 | **是** ❌ 误杀 |
| 「M7 的四个改进累积测量，**不是**各自独立对比 baseline：」 | **是** ❌ 误杀 |

判据很清楚了：**句子里有没有断言标记**（是 / 会 / 有 / 必须…）。
有的话它就是在断言，只不过恰好后面跟了一段示例。

修法：给"引出示例"那条加一个条件 —— 有断言标记就不算引导语。
**承诺数 200 → 204（找回 4 条），被拒 46 → 42。**
剩下那 42 条我逐条看过，**没有真承诺**。

> 这一步的价值不只是找回 4 条：它把"漏抽率可接受"从一句**无法检查的话**
> 变成了一个**测出来的数字**。

### 阶段测试中发现并修掉的缺陷

#### 缺陷一：输出被 `max_tokens` 截断，**整份文档的抽取全丢**（P0）

第一次真实运行：14 次调用里 **10 次**报「模型的输出不是合法 JSON」，
而错误里引用的"内容"是**模型原始输出的开头**。

根因：`max_tokens` 用了默认的 2000 —— 而一个 27 条声明的片段需要更多。
JSON 被砍掉一半 → `json.loads` 失败 → **那一整份文档的 27 条一条不剩**。

三处修法：

1. 抽取专用上限 `EXTRACT_MAX_TOKENS = 8000`（2000 是"一次对话"的量级，
   不是"一次结构化抽取"的量级）
2. **抢救被截断的 JSON**：扫括号配平，把完整的那些取出来 ——
   「被截断」只该丢掉尾巴，「格式坏」才该丢掉全部
3. **把 `finish_reason` 记下来**：之前完全没读它，于是"被截断"和"格式坏"
   在日志里长得一模一样，而处理方式完全不同

修完：承诺从 65 涨到 677（后来又因为下面的收紧降回 200）。

#### 缺陷二：过度抽取 —— 725 条里大量是噪音（P0）

截断修好之后暴露了相反方向的失败：**725 条声明，其中 677 条标成承诺**。
任务清单的勾选项、里程碑表格的行、目录树片段全被算成了承诺。

**第一步（提示词）**：加一条尖锐的判据 ——

> 我打开这个仓库，怎么知道它是真是假？

并写明七类排除项。效果：725 → 323。**79.8%**。

**第二步（代码，而不是继续磨提示词）**：加**结构性核对**。
引用是真的，不代表它是一条断言 —— 而下面这些**代码一眼就能认**：

| 过滤器 | 拦什么 |
| --- | --- |
| 制表符（`│├└─`） | 目录树 / 结构图片段 |
| `\|---\|` 形状 | 表格分隔行 |
| `- [ ]` / `- [x]` | 清单勾选项（进度记录） |
| 围栏代码块内 | 示例，不是断言 |
| 「流程 / 约定 / 规范 / 评审」章节下 | **对人**的要求，打开仓库验证不了 |

效果：79.8% → **84.3%**。

**第三步（标记词核对）**：再加四条规则，词表放在**数据文件**里：

| 规则 | 拦什么 | 效果 |
| --- | --- | --- |
| 以问号结尾 | 提问没有真假可言 | 拒 |
| 以 `：` 结尾 + 下一行是代码块 | 引出示例的引导语 | 拒 |
| 以祈使动词开头（读/用/把…） | 给**读者**的指令 | 拒 |
| 含「验收/关键路径」**且**无完成标记 | **标准不是现状** → 强制标成 plan | 移出承诺 |

效果：84.3% → **89.7%** ✅

> **这一步的教训值得单独说：能用代码确定性地判的事，不该交给提示词反复叮嘱。**
> 提示词里写三遍"不要抽目录树"，不如一行 `any(c in quote for c in "│├└─")`。
> 而且代码那条**可以写正反例测试**，提示词那条只能靠祈祷。

**分寸感也要说清**（每一条都配了反例测试）：

- 章节过滤按**章节**而不是按**文档**判 —— `DEV.md` 里既有「开发流程」（该拦）
  也有「依赖怎么装」（该放）。按文档一刀切会把后者也误杀
- 祈使动词要求**后面跟空格或反引号** —— 中文里"读文件"和"读 `x`"是两种语气。
  只看首字的话，「看起来」「读数」都会被误杀
- 「验收」有**完成标记**（✅/已完成/通过）时不强制成 plan ——
  「M1 验收通过 ✅」是**事实**，不是标准。少了这条例外会把一批真承诺误标成计划，
  而误标之后它们再也不会被验证，且不会有任何报错

#### 缺陷三：`_find_line` 的跨行匹配永远返回**最后一行**（P0）

`starts` 里存的是 `len(pieces)` —— 那是**元素个数**（每行一个），
不是**字符偏移**。于是跨行引用命中的行号永远是最后一行。

为什么危险：**行号错了不会有任何报错**。下游拿着一个看起来合理的错位置
去核对，会得出一个错的结论 —— 而我在模块文档里恰好写了
"行号由代码算，因为错行号是最危险的一类"。

它只在跨行时出现，而绝大多数引用是单行，所以藏得很深。
**是 D2 那条"跨行引用也要能找到"的测试把它逼出来的。**

#### 缺陷四：`write_knowledge` 在 Windows 上把 `\r\n` 写成 `\r\r\n`（P1）

测试夹具用 `write_text()` 默认的换行翻译，于是：
- 写 `\n` → 文件里是 `\r\n`
- 写 `\r\n` → 文件里是 `\r\r\n`

后果是"同一份内容"在 Windows 和 Linux 上字节不同 —— 而 CI 跑的是**双平台**。
修法：`newline="\n"`。

#### 缺陷五：分类表里两处机制打架（P1）

`CHANGELOG*` 既在**排除表**里、又被定义成 `metadata` 角色 ——
排除先命中，于是那条规则**永远不会生效**。

更重要的是排除本身是错的：排除掉之后，报告里"这个项目没有 CHANGELOG"
和"CHANGELOG 被排除了"**长得一模一样**。
按 S1 定下的原则（跳过 ≠ 没跑），应该发现它、标 skipped、让它显形。

**这条是测试抓出来的** —— 写测试的时候才发现自己的数据里有两套机制在抢同一件事。

#### 缺陷六：内容兜底用一个关键词就赢下整份文档（P1）

实测：preflight 自己的 `KNOWLEDGE.md`（讲不变量的设计文档）
因为里面提到了「回滚」这条**不变量**，被猜成了运维文档。

修法两条：① 至少要命中 **2 个不同关键词**；② 关键词只放**高精度短语**
（`部署步骤` / `回滚步骤`），不放孤立的词 —— `runbook` 单独一个词看着很运维，
但它在 preflight 自己的文档里是**规则名**（`general/no-runbook`）。

#### 缺陷七：自定义语料目录没带 `docs/roles.yaml` 被当成错误（P1）

`load_knowledge(custom_root)` 的语料目录通常只放几条规则，不会带文档分类表。
把它当错误，等于逼每个想加一条规则的人复制一份 `roles.yaml` ——
而复制出来的那份**永远不会跟着上游更新**。

修法：**文件不存在不是错误**，只有"存在但畸形"才是。
"自带的那份不能是空的"由测试守着（那是打包问题，不是运行时问题）。

#### 缺陷八：`markers` 做成可选参数会是一个静默失效（——）

新加的标记词核对需要调用方把词表传进来。第一版想给它一个默认值
（"不传就用空表"）—— 那等于让"忘了传"变成**核对悄悄不生效**，
而输出看起来完全正常。

修法：做成**必填的关键字参数**，并加一条测试用 `inspect.signature`
断言它没有默认值。

### 阶段测试中发现并修掉的缺陷

#### 缺陷一：`lstrip("./")` 把开头的点也吃掉了（P0）

`normalise_path` 用了 `lstrip("./")` —— 那是按**字符集**剥离，不是剥前缀。
于是 `.venv/pip.ini` 变成 `venv/pip.ini`，一条**正确**的证据被判成"路径不存在"。

在 fivewhys 上立刻显形：`.venv/pip.ini` 被报了漂移。

修法：只剥**字面量**的 `./` 前缀。

#### 缺陷二：散文里的缩写词被当成符号名（P0）

第一版的判据是"有大写字母就算符号"，于是「**OpenAI** 兼容端点」里的 `OpenAI`、
「**LLM** 调用」里的 `LLM` 全被收进来 —— 然后当然找不到，
于是一批**正确**的声明被判成漂移。

修法：收窄成"下划线 / 点号 / 括号调用"。
代价是 `ToolRegistry` 这种纯驼峰认不出来了 —— **那个代价是故意接受的**：
认不出来只是少一条证据，认错会让正确的声明变成假漂移。

#### 缺陷三：路径被**同时**当成符号（P0）

`scripts/setup.ps1` 既被当成路径（找得到）又被当成符号（尾段是 `ps1`，找不到）
—— 一条本该兑现的声明被自己的路径判成了漂移。

`demo_m1.py` 同理：里面的 `demo_m1` 含下划线，被当成独立符号找了一遍。

修法：符号候选不能是任何路径候选的子串。

#### 缺陷四：口径不一致时"对不上"被当成了漂移（P0）

实测两类：

- 「**19 个测试**」数出 17 个**函数** —— 参数化会把一个函数变成好几个用例
- 「**5 个工具**」数出 7 个 **.py 文件** —— 目录里还有 `__init__.py` / `_render.py`

两边说的根本不是一回事。判成漂移会让人去改一份**本来正确**的文档 ——
而那比"查不了"糟得多。

修法：给计数目标加一个 `exact` 标记（数据），**口径不精确时只报"查不了"**。

#### 缺陷五：数字取错了（P0）

第一版取"句子里最后一个数字"，于是「用最宽参数压测五个工具，最大返回
5950 字符（线是 6000）」里，它拿 **6000** 去核"工具个数"。

改成"紧挨着计数关键词的数字"，窗口从 12 收到 **4** —— 12 太宽，
上面那句话里 5950 又会被捞进来。

#### 缺陷六：文档里的相对路径不一定是相对仓库根（P0）

fivewhys 的评审文档写「子包齐全（`agent/` `mock/injectors/` `tools/`）」——
那三个目录其实在 `src/fivewhys/` 下面。

修法：找不到时依次试**包根目录**（有 `__init__.py` 的目录、`src/<包名>`），
以及**裸文件名按名字全仓库找**。

#### 缺陷七：同一个问题有两个答案（P0）

结论用的 `exists_in_repo`（会试包根目录）和证据核对用的 `_check_path`
（只看仓库根）**不是同一个函数** —— 于是同一条声明里，
结论说"路径找到了"，紧接着证据核对说"路径不存在"，
最后被降级成"查不了"。**用户看到的是自相矛盾的两句话。**

修法：`_check_path` 直接调 `exists_in_repo`。
修完"证据没通过核对"从 5 条降到 **0 条**。

#### 缺陷八：测试夹具本身不是合法 Python（P1）

`test_guard.py` 的夹具内容是 `line one` / `line two` —— 那是**语法错误**
（两个标识符挨在一起），于是 `Repo.parse` 返回 `None`，符号核对整条失效。

**测试夹具不合法时，失败信息会指向被测代码，而真正的问题在夹具里** ——
那会浪费很多时间。

#### 缺陷九：裸斜杠 `/` 被当成了路径（P1）

`looks_like_path` 只要有 `/` 就算路径，于是 markdown 里的 `/` 变成了
"仓库里不存在的路径"，一堆正确的声明被判成漂移。

修法：路径必须**有文件的样子** —— 以扩展名结尾，或以 `/` 结尾（明确在说目录）。

命中了 `BaseModel` / `Database` / `base_url`，一个**没有数据库的项目**
被"探测"出了关系数据库机制。

在五 whys 上立刻显形：`Base` 命中了 `injectors/_base.py` 里的一个基类。

修法：精确匹配（大小写不敏感），点号形式看最后一段。

#### 缺陷二：**工具把自己讲机制的文档当成了"本项目用了它"的证据**（P0）

preflight 自己的 `docs/KNOWLEDGE.md` 里有一张讲机制的表格，里面写着「多区域」
—— 于是探测到 preflight **有多区域机制**。

同类问题还有符号名撞车。**这两种误报都会让用户觉得"这个工具在瞎报"** ——
而那是最致命的一种失败：用户不会再跑第二次。

修法：**只有弱线索不算探测到**。要算探测到，至少得有一条
依赖 / 配置层面的线索。弱线索单独进 `uncertain`，连同理由一起报出来 ——
用户扫一眼就知道"哦，它只是看到我文档里提了一句"。

#### 缺陷三：YAML 修复脚本把 `docs/roles.yaml` 改坏了（P0）

我给机制 YAML 写的"给以 `*` 开头的值加引号"脚本，**把 glob 模式也当成了一类**：

```
- "**/SECURITY*"   →   '"**/SECURITY*      ← 前面的引号被粘上去了
```

于是 S4 的文档分类规则全坏掉，6 个测试红了。

**教训**：一个"看起来只改一种东西"的批量脚本，会在**你没预料到的形状**上生效。
而且它改的是**另一份数据文件** —— 那一轮本来根本没打算动它。

修法：从 git 恢复那个文件。**这类脚本的产出必须逐个文件看 diff**，
不能只看"共修了 N 个文件"。

#### 缺陷四：YAML 里以 `*` 开头的值会被当成别名引用（P2）

`why: **没演练过的备份等于没有备份**` —— YAML 把开头的 `*` 读成别名，
直接语法错误。而**多行值更麻烦**：加引号之后原来的"折叠标量"就不再合法。

修法：改成单行 + 引号（并用「」代替内层的英文引号）。

#### 缺陷五：`any_of` 里以 `:` 结尾的探针词被解析成映射（P2）

`- region:` / `- schedule:` / `- replicas:` 在 YAML 里是**映射**不是字符串。
而且那几个词本身也太泛（`region` 会命中一切）。

修法：换成 `aws_region` / `CronJob` / `replica_count` 这类更具体的词。

#### ①.5 一个"只在容器里红"的测试，最后判定是**测试错了**（P1）

上面那条 3.11 跑通之后，**只剩一条失败**：

```
AssertionError: import preflight.detect **多带进了**这些：['socket']
```

而它在本地绿、在 3.13 容器里也绿，**只**红在 3.11 容器里，而且只红在
`socket` 上 —— `httpx` / `openai` / `litellm` / `requests` 一个都没有。

**排查过程（记下来因为它没成功）**：我写了三个脚本想找出是谁 import 的
`socket`，三个都因为 PowerShell → docker → `python -c` 的引号解析**自己的脚本先坏了**。
最后停在"知道它不是我们的代码，但不知道具体是谁"。

**判定依据**：

| 证据 | 结论 |
| --- | --- |
| 源码扫描（逐文件扫 AST）**两边都绿** | **我们自己的代码没有 `import socket`** —— 这是直接证据 |
| 运行时检查只在容器里红，且只有 `socket` | 那是**间接**被带进来的 |

**修法**：把两个问题**分开问**（不是放宽断言）：

| 名单 | 用在哪 | 含 `socket` 吗 |
| --- | --- | --- |
| `FORBIDDEN_MODULES` | 源码扫描（AST） | **含** —— 显式 `import socket` 就是缺陷 |
| `FORBIDDEN_AT_RUNTIME` | 运行时间接检查 | 不含 |

为什么 `socket` 在运行时那一侧是**错的代理**：它是最底层的 stdlib 模块，
任何东西都可能顺手带进来。而"某个依赖 import 了 socket"不是我们这一层的缺陷 ——
我们既没碰网络，也没法控制它的依赖图。

**对 `socket` 的真正约束一条都没删** —— 源码那条还在，而且更严（连名字都不许出现）。

### 缺陷详录

#### 缺陷一：wheel 从 S0 起就构建不出来（P0，**上线阻塞**）

```
ValueError: A second file is being added to the wheel archive
at the same path: `preflight/knowledge/claims/verification.yaml`.
```

`packages = ["src/preflight"]` 已经把 `knowledge/` 打进 wheel 了，
而我又写了一条 `force-include` 把它再打一遍 → 重复路径 → 构建失败。

**为什么拖了八个阶段**：开发全程用 `pip install -e .`，**那根本不构建 wheel**。
而"本地能跑"和"装得上"是两件事 —— 后者只有真去构建一次才知道。

修法：删掉那条多余的 `force-include`（它的注释担心"YAML 进不了 wheel"，
而 hatchling 的 `packages` 包含目录下**所有**文件，不按扩展名过滤）。

**加了一条测试真的去构建一次 wheel 并检查内容** —— 任何"检查 pyproject 配置"
的替代方案都发现不了这个 `ValueError`。

#### 缺陷二：`demo_files` 把字节码当文本读（P0）

`preflight-check demo` 装完之后直接崩：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xf3 in position 0
```

`root.rglob("*")` 把 pip 字节码编译产生的
`preflight/demo/__pycache__/__init__.cpython-313.pyc` 也收进来了。

修法：`_is_source_file()` 跳过 `__pycache__` 和 `.pyc/.pyo/.so`。
**并且加了单元版本**（测那个函数，而不是测"wheel 里没有 pycache"）——
因为"今天 wheel 里没有"是事实，"读到字节码要跳过"是这条代码的性质。

#### 缺陷三：rich 在窄终端里折断长路径（P0）

Linux 上一条 S0 就有的测试红了：

```
assert 'a-rule.yaml' in ".../rules/a-r\nule.yaml"
```

rich 按终端宽度**软换行**，把路径折成两行。后果不只是测试红 ——
**用户复制那个路径会拿到垃圾**。

修法：路径和字段路径两行加 `soft_wrap=True` —— 那是我们自己产出的、
有精确含义的东西，不能让渲染层去折它。

**并加了一条把终端宽度固定成 40 列的测试**，而且**验证过它去掉修复就红**。

> 这一条值得单独记：一个"只在特定终端宽度下出现"的 bug，
> 不固定宽度的测试就是碰运气。而它在 Windows 上绿了八个阶段。

#### 缺陷四：**查重查出真冲突 —— CLI 和导入包的名字都被占了**（P0，未解决）

**这是 PF-47 的结论，而且比预想严重。**

| 名字 | 状态 |
| --- | --- |
| PyPI `preflight` | 占用（2015 年的 Django 项目） |
| PyPI `preflight-gate` | **占用，而且活跃** —— 2026-09-01 发布 0.7.0，已有 0.8.0a2 |
| PyPI `preflight-ai` / `precheck` / `shipcheck-cli` / `launchcheck` | 全被占用 |
| GitHub `preflight` | 多个同名仓库（`felixgeelhaar/preflight`、`preflightsh/preflight`） |

**`preflight-gate` 的 README 里明写着：**

> The distribution is `preflight-gate`; **the import, the command, and the
> manifest schema are all `preflight`**. PyPI's `preflight` is an unrelated
> Django project last released in 2015, so that name was never available.

也就是说，它已经占用了 **`preflight` 这个导入包名和命令行名**。
而它的定位（**agent 工具信任边界**）和我们的目标用户**完全重叠**。

**具体后果**：`pip install preflight-check` 和 `pip install preflight-gate`
同时装的话，两者都提供 `preflight/` 这个导入包和 `preflight` 这个命令 ——
**pip 会互相覆盖文件**，谁后装谁赢。这比"命令被抢"更糟：
它是**静默的模块级覆盖**。

**这是一个必须改名才能发布的问题**，而改名是一次 70+ 文件的机械改动。
**本轮没有做**，理由写在「为什么没发布」里。

### 为什么没发布（PF-48 未做）

三条，按重要性排：

1. **名字冲突没解决**（上面缺陷四）。改名要动 70+ 文件的包名、导入、CLI、文档、
   测试，是一次有风险的机械改动 —— **不该在发布这一步顺手做**。
   而且这是个需要你拍板的决定（叫什么名字是你的项目的第一印象）。
2. **没有 PyPI 凭证**，也不该由我替你注册和上传。
3. **CI 仍然一次都没跑过** —— 下面那条"CI 全绿"只做到了它的**等价物**（Linux 容器），
   不是真的绿。把一个"从没在 CI 上绿过"的包推到 PyPI，是在拿别人的环境做实验。

**已经准备好的**：wheel 能构建了、内容验证过了、`pip install .` 在干净容器里能跑、
Docker 镜像能跑 demo。**只差名字和凭证。**

### ⭐ 阶段测试结果（PLAN 的四条，逐条对照）

**① 干净环境测试：全新容器 → pip install → 跑 demo → 成功** ✅

```
$ docker build -t preflight:dev .
$ docker run --rm preflight:dev

preflight-check demo　档案 agent-enterprise　（零 LLM、零联网）

🔴 broken-agent　15 条发现（agent 专项 14 条）　判定 NO-GO
🟢 clean-agent　0 条发现（agent 专项 0 条）　　判定 INCOMPLETE　（3 条规则依赖外部工具，这台机器上没装）
```

**这份输出是整个项目最有说服力的一屏**：两份 agent 的文件结构完全一样，
差别只在几行保护代码上。

**② 离线测试** ✅ —— `preflight-check demo` 不读环境变量、不联网、不调模型。
容器的 `pip install` 装在构建期，运行期一个网络请求都没有。

**③ 文档一致性** ✅ —— 三条测试：
- 每个 PF 编号在 PROGRESS 里都有记录
- 每个阶段（S0–S8）都有一节
- 所有 markdown 里的相对链接都不是死链
- README 里提到了每一个 CLI 命令

> 死链那条测试**自己先错了一次**：朴素的 markdown 链接正则把
> `` `tools[call.name](**call.args)` `` 这行 **Python** 当成了链接，
> 于是两份本来正确的文档被判"有死链"。
> **修的是检测器，不是文档** —— 文档没问题，是检测器把代码当成了散文。

**④ CI 全绿** ⚠️ **只做到等价物** —— 在 Linux 容器里跑了全套：

```
$ docker run --rm -v ...:/src -w /src python:3.13-slim \
    sh -c "pip install -e '.[dev]' && python -m pytest -q"
```

跑出了上面那三个"只在装完之后出现"的问题，还包括那个
**只在 Linux 的 80 列终端下暴露**的折行 bug。

**但这不是 CI。** CI 会在 Ubuntu **和 Windows** 上、Python **3.11 和 3.13** 上跑 ——
四个组合。而项目从 S0 到今天，**一个组合都没在 CI 上跑过**。
