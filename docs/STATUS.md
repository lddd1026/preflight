### 模块化与可扩展性（12 条测试守着）

这两个性质是**同一件事的两面**：加东西不用改代码，是因为模块之间没有乱牵。

**依赖图**（用 AST 读真实 import，不是照文档说）：

```
cli(5)         → core  demo  detect  interact  runtime  understand
understand(3)  → core  detect  runtime
detect(2)      → core
interact(4)    → core
```

**没有向上依赖，也没有环。** `cli` 是唯一的组合根。

**可扩展性是真的加过一遍验证的**，不是推断的：

| 加什么 | 要改代码吗 |
| --- | --- |
| 一条规则 | ❌ 只写 YAML |
| 一个机制（带探测线索 + 矩阵格子） | ❌ 只写 YAML |
| 一条不变量 | ❌ 只写 YAML |
| 一个档案 | ❌ 只写 YAML |
| 跨档案拉一条规则（`include`） | ❌ 只写 YAML |
| **一个全新的检测能力** | ✅ **要写代码** —— 检查器就是「怎么查」，它得有实现 |

最后一行是**设计，不是缺陷**，但边界必须**显式**：写错 checker 名字会在
**加载期**报错，并列出全部可选项 ——

```
detect.checker  没有叫 'totally-made-up-checker' 的检查器。
全部可用：agent-loop-guard, config-name-drift, cost-source, exists, …
```

**静默失败是最坏的一种**：规则看起来配好了、跑起来不报，
于是所有人以为「查过了，没问题」。

## 能跑什么

```powershell
pip install preflight-check-cli

preflight-check demo                    # ⭐ 离线：不配 API Key、不联网就能看到对比
preflight-check run .                   # 确定性检查（零 LLM）
preflight-check mechanisms .            # 探测机制 + 推导该查什么（带推理链）
preflight-check review . --today …      # 一次完整评审 → RELEASE_REVIEW.md
preflight-check waive <规则> --who … --why … --expires …
preflight-check waivers .               # 豁免审计
```

**离线 demo 的样子**（`docker run --rm preflight-check`，这是 README 第一屏）：

```
preflight demo　档案 agent-enterprise　（零 LLM、零联网）

🔴 broken-agent　15 条发现（agent 专项 14 条）　判定 NO-GO
🟢 clean-agent　0 条发现（agent 专项 0 条）　　判定 INCOMPLETE
```

两份 agent 的**文件结构完全一样**，差别只在几行保护代码上：
一次 `try`、一个 `Semaphore`、一句告诉模型「被截断了」的话。

### 名字：为什么命令叫 `preflight-check`

`preflight` 这个**导入包名和命令名**被活跃项目
[`preflight-gate`](https://pypi.org/project/preflight-gate/) 占着
（它的 README 明写「the import, the command, and the manifest schema are
all `preflight`」），而两者目标用户完全重叠 —— 同时安装会**静默互相覆盖模块文件**。

| | 名字 |
| --- | --- |
| 项目 / 仓库 | `preflight` |
| 分发 | `preflight-check-cli` ← 见下 |
| 导入包 | `preflight_check` |
| 命令 | `preflight-check` |
| 评审记录目录 | `.preflight/` |

**分发名为什么还带 `-cli`**：`preflight-check` 在 PyPI 上注册不了 —— 那条「名字太相似」
检查会把 `-` `_` `.` 全删掉、再把 `l/L/i/I` 换成 `1`、`o/O` 换成 `0`，然后**全等比较**，
而它与已存在的 [`pre-flight-check`](https://pypi.org/project/pre-flight-check/)
（v1.4.0，活跃的同赛道项目）归一化后是同一个字符串。去掉连字符也救不了
（`preflightcheck` 归一化后还是它）。

代价只有 `pip install` 那一行 —— **命令名和导入名都没变**，
收益是它能和 `preflight-gate` 装在同一台机器上而互不影响。

## 这个项目最值钱的产出不是那 29 条规则

是 [PITFALLS.md](PITFALLS.md) 里那 18 条血案。挑三条最典型的：

**① 有一整类问题只在「装完之后」出现。** wheel 从 S0 起就构建不出来，
而本地全程用 `pip install -e .` —— **那根本不构建 wheel**。拖了八个阶段，
是 Docker 干净容器第一次逼出来的。同一类还有：把 `__pycache__` 当文本读、
`CMD` 用的是已经不存在的命令名（**镜像构建成功、容器起不来**）。

**② 「对不上」不等于「错了」。** 文档说「5 个工具」我数出 7 个 `.py` 文件
（目录里有 `__init__.py`）；文档说「19 个测试」我数出 17 个函数（参数化会放大）。
**判成漂移会让人去改一份本来正确的文档 —— 那比「查不了」糟得多。**

**③ 靠人记得的纪律，迟早会忘。** 这一条刚刚被验证过一次：
四条纪律里有三条在审计之前**没有任何东西在守**。
